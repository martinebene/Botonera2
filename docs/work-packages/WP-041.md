# WP-041 - Eventos recientes con nivel fijo y evento más nuevo primero

## Estado documental

`APROBADO`

## Objetivo

Ajustar el cuadrante `Eventos` de `/moderacion/` para que el nivel visible permanezca siempre accesible fuera del área scrolleable y los eventos se presenten con el más reciente primero, manteniendo una lista compacta, legible y confinada al scroll interno del panel.

El cambio es exclusivamente de presentación y navegación local sobre `EstadoModeracion.eventos_recientes`. No altera auditoría, backend, contratos, niveles ni semántica institucional.

## Dependencias

- WP-036

## Fuentes canónicas obligatorias

- `AGENTS.md`;
- este WP;
- `docs/05-frontend-moderacion.md`, especialmente las secciones de Eventos, Responsive y Reconexión;
- `docs/work-packages/WP-024.md`;
- `docs/work-packages/WP-036.md`;
- `apps/moderacion/app/components/PanelEventos.vue`;
- `apps/moderacion/app/components/PanelContenedor.vue`;
- tests Vitest/Playwright existentes de Moderación y Eventos;
- proyección `EstadoModeracion.eventos_recientes`;
- DEC-001, DEC-003, DEC-007 y DEC-017.

Como referencia visual/funcional puede consultarse el panel de eventos del sistema histórico conforme DEC-001, sin copiar su arquitectura, polling o contratos.

## Decisiones humanas cerradas

HUMAN_GATE aprobó:

1. los eventos se muestran con el **más nuevo arriba**;
2. no aplica una política especial de “mantener posición si el usuario mira eventos viejos” asociada al orden cronológico ascendente;
3. el selector de nivel `L3/L2/L1` se ubica en la **cabecera del propio panel**, siempre visible y fuera del área scrolleable.

Se conserva sin cambios:

- filtro inicial `L3`;
- `L3` = solo principales;
- `L2` = L2 + L3;
- `L1` = L1 + L2 + L3;
- scroll interno únicamente en la lista de eventos;
- cada evento conserva `seq`, timestamp, nivel, etiqueta, código y mensaje.

## Alcance

### 1. Orden visual descendente

`EstadoModeracion.eventos_recientes` continúa siendo autoritativo y puede llegar en el orden definido por backend.

El frontend debe derivar una colección visual que muestre:

- mayor `seq` primero;
- menor `seq` al final.

No mutar el array recibido en props ni mantener una historia local paralela.

La implementación debe ser determinista aunque el snapshot recibido ya venga ordenado o sea reemplazado por reconexión.

### 2. Evento nuevo siempre visible

Cuando el snapshot incorpore uno o más eventos con `seq` superior al máximo previamente observado, la lista debe volver al inicio de su scroll para que el evento más reciente quede visible inmediatamente.

Esto aplica al flujo normal de actualización y no requiere polling nuevo.

No se debe implementar scroll al final porque el orden visual es descendente.

Un mero cambio de filtro no debe inventar eventos ni alterar la colección autoritativa.

### 3. Selector de nivel fijo en cabecera

Mover el control `Nivel visible` fuera del cuerpo scrolleable y ubicarlo en la cabecera del panel utilizando la capacidad de acciones de `PanelContenedor` o una solución equivalente.

Debe quedar visible aun cuando la lista esté desplazada.

El control puede ser un `select` compacto o una alternativa de densidad equivalente, siempre que conserve exactamente los tres estados:

- Principales (L3);
- Intermedios (L2+L3);
- Sistema (L1+L2+L3).

No cambiar la semántica acumulativa del filtro.

### 4. Lista y scroll

El cuerpo de eventos debe:

- ocupar la altura disponible;
- mantener `overflow` confinado al listado;
- no aumentar la altura del cuadrante;
- no hacer scrollear el selector de nivel;
- no provocar scroll de página en el shell desktop ya resuelto por WP-036.

El listado debe contar con una referencia DOM explícita si es necesaria para controlar `scrollTop`.

### 5. Densidad de las tarjetas

Compactar razonablemente cada evento para mostrar más actividad simultánea sin perder información.

Cada tarjeta conserva de forma legible:

- `#seq`;
- timestamp;
- nivel L1/L2/L3;
- etiqueta;
- código de evento;
- mensaje.

Se permite reducir paddings, gaps y tamaños secundarios.

No eliminar ni esconder permanentemente ninguno de esos datos.

### 6. Estados vacíos

Cuando no existan eventos:

- mostrar un estado vacío compacto.

Cuando existan eventos pero ninguno coincida con el filtro:

- indicar claramente que no hay eventos para el nivel seleccionado.

No reservar una altura excesiva para explicaciones.

### 7. Reconexión y reemplazo de snapshot

Ante reconexión o reemplazo completo de `eventos_recientes`:

- la UI deriva nuevamente el orden y filtro desde el nuevo snapshot;
- no conserva eventos que el backend ya no proyecta;
- no acumula historia local;
- si el nuevo snapshot contiene un evento más reciente que el máximo previamente observado, se posiciona arriba;
- si el contexto se reinicia y la secuencia vuelve a un conjunto distinto/menor, adoptar el snapshot sin intentar mezclarlo con el anterior.

### 8. Accesibilidad y feedback visual

El selector debe conservar label accesible.

La lista debe poder recorrerse normalmente con rueda/touchpad/teclado conforme al comportamiento nativo del contenedor.

No introducir animaciones que retrasen o escondan la llegada de un evento reciente.

- dependencias externas nuevas salvo escalamiento DT-038.

## Criterios de aceptación

1. El filtro inicial sigue siendo `L3`.
2. `L3` muestra solo L3.
3. `L2` muestra L2+L3.
4. `L1` muestra L1+L2+L3.
5. Los eventos filtrados se muestran por `seq` descendente.
6. El evento de mayor `seq` queda primero.
7. Al llegar un evento nuevo de mayor `seq`, la lista se posiciona al inicio y el nuevo evento queda visible.
8. El selector de nivel permanece visible aunque la lista tenga scroll.
9. El selector no forma parte del área scrolleable.
10. Solo la lista de eventos utiliza scroll interno.
11. El panel no deforma la grilla ni genera scroll de página a 1366×768.
12. Cada evento sigue mostrando seq, timestamp, nivel, etiqueta, código y mensaje.
13. Las tarjetas son más compactas que la baseline previa sin perder legibilidad.
14. Reconexión/reemplazo adopta exclusivamente el snapshot vigente.
15. No se acumula una historia local paralela.
16. No se modifica backend, contrato, SSE ni auditoría.
17. No se agregan dependencias externas nuevas salvo DT-038.

## Pruebas obligatorias

### Vitest / Vue

Agregar o ajustar pruebas DOM que cubran al menos:

- filtro inicial L3;
- semántica acumulativa de L2 y L1;
- snapshot en orden ascendente renderizado en descendente;
- snapshot ya descendente sin duplicados ni mutación de props;
- llegada de un evento nuevo y `scrollTop === 0`;
- reemplazo completo de snapshot;
- reinicio de contexto/secuencia sin acumulación local;
- selector ubicado en cabecera y no dentro del contenedor scrolleable;
- estado sin eventos;
- estado sin coincidencias para el filtro;
- datos completos de cada tarjeta.

### Playwright

Agregar/ajustar un recorrido de Moderación que demuestre:

1. suficiente cantidad de eventos para producir scroll interno;
2. selector L3/L2/L1 visible antes y después de desplazar la lista;
3. orden descendente por `seq`;
4. llegada de un evento nuevo y retorno al inicio;
5. selector operable después del scroll;
6. shell sin scroll de página a `1366 × 768`;
7. verificación representativa a `1920 × 1080`.

La comprobación debe inspeccionar overflow/scroll real, no limitarse a clases CSS.
