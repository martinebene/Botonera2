# WP-020 - Remapeo rápido físico a dispositivo lógico coordinado por backend

## Estado documental

`BORRADOR`

## Objetivo

Implementar el flujo coordinado de remapeo rápido de un teclado físico hacia un identificador lógico `devXX` existente, iniciado desde Moderación a través de FastAPI y ejecutado por el `device-bridge`, permitiendo al operador confirmar el cambio como `TEMPORAL` o `PERSISTENTE` sin interrumpir el tráfico normal de los demás dispositivos ni alterar identidad, presencia, votos o palabra.

## Resultado esperado

Al integrar este WP debe existir un contrato backend/bridge completo y testeable que permita:

- iniciar una única operación de remapeo para un `devXX` del padrón activo;
- mantener funcionando normalmente todos los fingerprints ya mapeados mientras el bridge espera candidato;
- capturar exclusivamente un fingerprint elegible no mapeado mediante su primer `keydown`;
- exponer el candidato en `EstadoModeracion` y propagar su cambio mediante el mecanismo REST snapshot + SSE ya existente;
- cancelar sin mutar mapping;
- confirmar el candidato eligiendo `TEMPORAL` o `PERSISTENTE`;
- aplicar un cambio temporal solo en memoria del bridge;
- aplicar un cambio persistente mediante reemplazo atómico y validado de `devices.json`;
- auditar antes de autorizar cualquier aplicación confirmada;
- reconciliar comandos de control mediante un `remapeo_id` idempotente;
- conservar íntegramente las reglas de negocio en FastAPI.

La UI visual de Moderación no se implementa todavía: este WP entrega los contratos y tipos que esa interfaz consumirá posteriormente.

## Dependencias

- WP-019 `INTEGRADO`: bridge físico Linux, fingerprint, mapping efectivo, `devices.json` y captura `evdev` ya disponibles.
- WP-017 `INTEGRADO`: `EstadoModeracion`, revisión monotónica y SSE ya disponibles para publicar el estado del remapeo.
- WP-018 `INTEGRADO`: OpenAPI versionado y `api-client` TypeScript derivado ya disponibles para mantener sincronizado el nuevo contrato REST.
- DEC-015 `APROBADA`: contrato base del bridge físico.
- DEC-016 `APROBADA`: contrato de coordinación, captura no bloqueante y persistencia seleccionable del remapeo.

## Alcance

### 1. Estado de remapeo en backend

Incorporar al estado operativo del backend una única operación de remapeo activa, con identidad `remapeo_id` UUID y datos mínimos necesarios para Moderación.

El estado debe distinguir conceptualmente al menos:

- captura en curso;
- candidato físico disponible;
- confirmación/aplicación en progreso cuando corresponda.

No debe persistirse como sesión recuperable después de reiniciar FastAPI: el backend sigue usando estado operativo en memoria conforme DT-004/DT-009.

### 2. Estados en los que puede iniciarse

Permitir iniciar remapeo únicamente en:

- `PREPARANDO`;
- `SESION_ABIERTA`, incluida una votación activa.

En `SIN_PREPARAR` debe rechazarse con error funcional estable.

El backend debe validar que el `devXX` solicitado pertenece al padrón activo/congelado. No se permite crear un dispositivo lógico nuevo desde este flujo.

### 3. Contrato REST de Moderación

Implementar las capacidades canónicas:

```text
POST   /api/v1/remapeos
POST   /api/v1/remapeos/{remapeo_id}/confirmacion
DELETE /api/v1/remapeos/{remapeo_id}
```

Body de inicio:

```json
{
  "dispositivo": "dev05"
}
```

Body de confirmación:

```json
{
  "persistencia": "TEMPORAL"
}
```

con `persistencia` estrictamente limitada a:

```text
TEMPORAL
PERSISTENTE
```

Los bodies son cerrados (`extra="forbid"`) y los strings relevantes son estrictos/no vacíos según el contrato.

Los errores funcionales deben usar códigos estables. Como mínimo deben poder distinguir:

- estado global incompatible;
- dispositivo lógico inexistente en el padrón activo;
- otro remapeo ya en curso;
- `remapeo_id` no coincidente;
- confirmación sin candidato;
- bridge no disponible;
- aplicación/persistencia rechazada por el bridge;
- auditoría no disponible.

Los nombres finales de códigos deben quedar documentados y testeados, sin reutilizar códigos con semánticas distintas.

### 4. Endpoint interno bridge -> backend para candidato

Implementar un endpoint backend interno vinculado al `remapeo_id` para que el bridge informe el candidato capturado.

Debe aceptar únicamente un candidato correspondiente a la operación activa y no debe permitir aplicar el remapeo por sí mismo.

La confirmación humana posterior sigue siendo obligatoria.

El frontend no usa este endpoint directamente.

### 5. API de control local del bridge

Agregar al `device-bridge` un pequeño servidor HTTP de control utilizando únicamente biblioteca estándar de Python.

Debe escuchar en loopback por defecto y permitir configuración técnica de host/puerto sin modificar código.

La superficie debe ser versionada y permitir como mínimo:

- iniciar captura para `{remapeo_id, devXX}`;
- consultar el estado de una operación por `remapeo_id` para reconciliación;
- confirmar/aplicar el candidato esperado indicando fingerprint y `TEMPORAL|PERSISTENTE`;
- cancelar.

Los paths internos concretos deben quedar documentados en el README del bridge y sus contratos cubiertos por tests.

No agregar FastAPI/Flask/aiohttp u otro servidor/framework al bridge.

### 6. Idempotencia de los comandos de control

El mismo `remapeo_id` identifica toda la operación.

Repetir el mismo comando con el mismo ID y parámetros debe ser seguro y no aplicar dos veces un cambio.

Usar el mismo ID con parámetros incompatibles debe rechazarse explícitamente.

Una respuesta HTTP perdida no puede producir un segundo remapeo. El backend debe poder consultar/reconciliar el estado del bridge antes de decidir que la aplicación es desconocida.

Esta idempotencia corresponde exclusivamente a los comandos de control. Las pulsaciones físicas normales continúan con la regla de WP-019: máximo un intento HTTP y cero retry.

### 7. Captura concurrente con operación normal

El modo captura no puede detener ni interceptar indebidamente los dispositivos ya mapeados.

Durante `CAPTURANDO` o `CANDIDATO`:

- las pulsaciones de fingerprints efectivamente mapeados siguen el flujo normal del bridge y llegan al backend;
- un fingerprint mapeado nunca puede convertirse en candidato;
- una votación, presencia, test o palabra puede continuar normalmente en los demás dispositivos;
- `keyup` y autorepeat continúan excluidos;
- un candidato se origina únicamente en un `keydown` de fingerprint elegible no mapeado.

La implementación debe ser thread-safe/serializada según corresponda porque la API de control local y el loop de captura física pueden ejecutarse concurrentemente.

### 8. Elegibilidad exacta del candidato

Un fingerprint puede ser candidato para el `devXX` objetivo solamente si:

1. no forma parte del mapping efectivo vigente de ningún dispositivo lógico; y
2. si aparece en `devices.json`, está asociado al mismo `devXX` objetivo.

Esto permite recuperar el fingerprint base después de un remapeo temporal, pero impide tomar como candidato la configuración base de otro concejal/dispositivo.

El primer candidato elegible queda congelado para esa operación hasta confirmar o cancelar. Otro dispositivo desconocido no lo reemplaza silenciosamente.

### 9. Remapeo temporal

Al confirmar `TEMPORAL`:

- reemplazar el fingerprint efectivo del `devXX` solo en memoria;
- dejar `devices.json` byte/semánticamente sin modificar;
- conservar todas las otras asociaciones;
- mantener el override hasta reinicio del bridge o hasta otro remapeo posterior del mismo `devXX`;
- no revertir automáticamente por cerrar sesión/cancelar preparación;
- después de reiniciar el bridge, reconstruir el mapping únicamente desde `devices.json`, eliminando el override temporal.

Debe poder volver al fingerprint base mediante un nuevo remapeo del mismo `devXX`.

### 10. Remapeo persistente

Al confirmar `PERSISTENTE`:

- construir un nuevo mapping base completo;
- retirar la asociación base anterior del `devXX` objetivo;
- agregar el candidato al mismo `devXX`;
- conservar sin cambio el resto de asociaciones;
- validar el mapping resultante con las mismas invariantes de `devices.json`;
- escribir de forma segura usando archivo temporal en el mismo directorio, flush/fsync y reemplazo atómico;
- instalar el nuevo mapping efectivo únicamente después de que la escritura persistente haya finalizado correctamente.

Si cualquier paso de persistencia falla:

- `devices.json` anterior debe permanecer utilizable;
- mapping efectivo anterior debe continuar vigente;
- la operación debe informar fallo técnico;
- no se acepta una degradación silenciosa a remapeo temporal.

Después de reiniciar el bridge, el nuevo fingerprint persistente debe seguir asociado al mismo `devXX`.

### 11. Auditoría antes de aplicar

Antes de autorizar al bridge a modificar el mapping, el backend debe persistir un evento L3 obligatorio que represente la confirmación/autorización humana e incluya al menos:

- `remapeo_id`;
- dispositivo lógico objetivo;
- fingerprint efectivo anterior conocido;
- fingerprint candidato;
- persistencia seleccionada.

El texto/código del evento no debe afirmar que la aplicación ya ocurrió antes de que el bridge la ejecute.

Si la auditoría falla:

- responder `503 AUDITORIA_NO_DISPONIBLE`;
- no enviar al bridge la orden de aplicación;
- no cambiar mapping temporal ni persistente.

Los eventos de inicio/candidato/cancelación pueden definirse dentro de la semántica de auditoría existente siempre que no creen afirmaciones institucionales falsas; la aplicación confirmada es la puerta obligatoria.

### 12. Fallos de coordinación

Distinguir al menos:

- bridge inaccesible al iniciar;
- bridge inaccesible al confirmar;
- rechazo técnico del bridge;
- timeout con resultado potencialmente incierto;
- persistencia fallida;
- operación ya aplicada/cancelada.

Ante una respuesta perdida después de confirmar, el backend debe usar `remapeo_id` y consulta de estado del bridge para resolver si el cambio fue aplicado, sin crear un nuevo ID ni volver a aplicar a ciegas.

No implementar rollback distribuido automático que pueda reasignar un teclado que ya empezó a generar pulsaciones con el mapping nuevo.

### 13. Proyección Moderación y SSE

Extender `EstadoModeracion` con un submodelo explícito de remapeo activo suficiente para que una futura UI pueda representar:

- ID de operación;
- `devXX` objetivo;
- estado;
- candidato cuando exista;
- información diagnóstica física segura para identificarlo.

No incluir este estado en `EstadoRecinto`.

Cada transición relevante del remapeo debe incrementar la `revision`/publicar el cambio por el mecanismo SSE canónico existente, sin introducir polling.

### 14. OpenAPI y api-client

Actualizar el snapshot OpenAPI versionado y regenerar los tipos TypeScript derivados conforme DEC-014.

Agregar al `ClienteModeracion` las operaciones públicas de remapeo necesarias para la futura UI.

El endpoint interno bridge->backend no debe incorporarse como método de alto nivel del cliente de Moderación aunque pueda existir en los tipos OpenAPI generados.

`ClienteRecinto` continúa estrictamente read-only y no expone remapeo.

### 15. Concurrencia con pulsaciones y mutaciones backend

Las mutaciones de estado backend asociadas al remapeo deben respetar el único `EjecutorMutaciones` y no crear una vía paralela que compita con voto/presencia/palabra.

Un remapeo no puede cambiar retroactivamente la identidad con la que se procesaron pulsaciones anteriores.

Una pulsación que el bridge entrega con `dev05` antes o después del cambio sigue siendo `dev05` para FastAPI.

### 16. Sin nuevas dependencias directas

No agregar nuevas dependencias directas Python, TypeScript o runtime para implementar este WP.

Usar biblioteca estándar para el control HTTP local y persistencia atómica del bridge.

Si aparece una necesidad real de otra dependencia, escalar DT-038 antes de incorporarla.

### 17. Logging y observabilidad

El bridge debe registrar claramente:

- inicio/cancelación de captura;
- candidato detectado;
- candidato rechazado por estar mapeado/no ser elegible;
- confirmación temporal/persistente;
- persistencia exitosa/fallida;
- reconciliación/idempotencia;
- fin de operación.

Estos logs son diagnósticos locales y no reemplazan el evento institucional obligatorio del backend.

## Criterios de aceptación

1. El remapeo solo puede iniciarse con preparación activa o sesión abierta.
2. El backend valida que el `devXX` objetivo pertenece al padrón activo.
3. Solo existe una operación activa y posee `remapeo_id` UUID estable.
4. El navegador no se comunica directamente con el bridge.
5. La API de control del bridge escucha loopback por defecto y no agrega dependencia nueva.
6. Todos los fingerprints mapeados continúan transmitiendo pulsaciones normales durante captura.
7. Ningún fingerprint efectivamente mapeado puede convertirse en candidato.
8. El primer fingerprint elegible queda como candidato y no se transmite como pulsación normal.
9. La configuración base de otro `devXX` nunca puede apropiarse como candidato aunque temporalmente no esté efectiva.
10. El fingerprint base del mismo objetivo puede usarse para volver de un remapeo temporal.
11. Cancelar no modifica mapping efectivo ni `devices.json`.
12. Confirmar exige `TEMPORAL` o `PERSISTENTE` explícito.
13. `TEMPORAL` modifica solo memoria y desaparece tras reinicio del bridge.
14. `TEMPORAL` no se revierte automáticamente al cerrar sesión.
15. `PERSISTENTE` reemplaza únicamente la entrada física del `devXX` objetivo en `devices.json`.
16. La escritura persistente es atómica/validada y un fallo conserva archivo y mapping efectivos anteriores.
17. Un remapeo persistente sobrevive reinicio del bridge.
18. Antes de aplicar existe un evento L3 durable de autorización con ID, viejo/nuevo fingerprint, devXX y persistencia.
19. Auditoría no disponible impide aplicar.
20. Los comandos de control son idempotentes por `remapeo_id` y una respuesta perdida puede reconciliarse sin doble aplicación.
21. Presencia, votos, identidad y palabra permanecen inalterados por el remapeo.
22. `EstadoModeracion` refleja operación/candidato; `EstadoRecinto` no expone información física de remapeo.
23. REST snapshot + SSE continúan siendo la sincronización de Moderación; no se introduce polling.
24. OpenAPI y tipos `api-client` quedan sincronizados; `ClienteModeracion` expone comandos públicos y `ClienteRecinto` no.
25. No se agregan dependencias directas.
26. La suite completa funciona sin hardware real, sin escribir destructivamente configuración versionada y sin conectividad externa.
27. Código propio nuevo respeta DEC-001 y flujos no triviales quedan documentados pedagógicamente en español.

## Pruebas obligatorias

Como mínimo cubrir:

### Backend

- `SIN_PREPARAR` rechaza inicio;
- `PREPARANDO` y `SESION_ABIERTA` aceptan inicio;
- inicio durante votación activa no altera la votación;
- `devXX` inexistente rechazado;
- segundo remapeo simultáneo rechazado;
- callback candidato con ID incorrecto rechazado;
- candidato actualiza `EstadoModeracion` y revisión/SSE;
- confirmación sin candidato rechazada;
- persistencia enum estricta y bodies cerrados;
- cancelación limpia;
- auditoría ocurre antes de ordenar aplicación;
- fallo de auditoría evita invocar bridge;
- timeout/respuesta perdida usa consulta de estado/idempotencia;
- presencia, votos y palabra invariantes antes/después.

### Bridge

- servidor de control ligado a loopback/configurable mediante fake o puerto efímero;
- inicio idempotente por ID;
- ID repetido con otro `devXX` rechazado;
- dispositivos mapeados siguen enviando mientras captura está activa;
- pulsar un mapeado nunca genera candidato;
- primer no mapeado elegible genera candidato;
- candidato posterior no reemplaza al primero;
- base del mismo objetivo elegible bajo override temporal;
- base de otro objetivo no elegible;
- `TEMPORAL` cambia mapping efectivo y no toca archivo;
- reinicio/recreación elimina override temporal;
- `PERSISTENTE` reemplaza exactamente el fingerprint del objetivo;
- persistencia usa archivo temporal/reemplazo atómico;
- simulación de error de escritura/fsync/replace conserva mapping/archivo anterior;
- reinicio carga mapping persistente;
- confirmación repetida del mismo ID no duplica escritura/cambio;
- cancelación no altera mapping;
- keyup/repeat continúan fuera de captura.

### Contratos/api-client

- endpoints backend y modelos OpenAPI;
- drift check OpenAPI/tipos;
- métodos públicos de `ClienteModeracion`;
- ausencia de mutaciones en `ClienteRecinto`;
- proyección pública sin fingerprint/remapeo.

## Invariantes y restricciones

- `fingerprint -> devXX -> concejal` conserva la frontera definida por DT-014/DEC-015.
- `devXX -> concejal` nunca cambia mediante remapeo.
- dispositivos mapeados siguen operativos durante captura.
- votos aceptados continúan irreversibles.
- el bridge no incorpora reglas de negocio.
- no hay conexión directa navegador -> bridge.
- no se agregan dependencias directas sin DT-038.
- no se implementan retries de pulsaciones ni replay durable.
- `devices.json` solo puede modificarse por confirmación humana explícita `PERSISTENTE` y mediante escritura segura.
- la confirmación debe auditarse antes de aplicar.
- se conserva un único worker/estado backend y la serialización canónica de mutaciones.
- código/comentarios respetan DEC-001; herramientas/fallbacks respetan DEC-003; entorno/agentes/revisión respetan DEC-007.
- el documento conserva el formato parseable de `FORMATO_WP_LANZADORES.md`.
