# WP-002 - Runtime base FastAPI, estado inicial y serialización

## Estado documental

`APROBADO`

## Objetivo

Crear el runtime base del backend FastAPI con un único estado operativo en memoria, estado inicial `SIN_PREPARAR` y un mecanismo único de serialización para futuras mutaciones.

## Resultado esperado

El backend puede arrancar y detenerse limpiamente, crea una única instancia de estado durante el `lifespan`, expone un health check técnico y ofrece una abstracción probada para ejecutar mutaciones en orden exclusivo, sin implementar todavía preparación, sesión, votación o entradas físicas.

- DT-004, DT-005 y DT-007 cerradas.

## Alcance

- Crear la aplicación FastAPI dentro de `apps/backend` con factory o estructura equivalente testeable.
- Usar `lifespan` para crear y destruir los recursos de aplicación.
- Definir el contenedor/objeto de estado global mínimo con estado inicial `SIN_PREPARAR` y sin entidades activas.
- Definir un único mecanismo asíncrono de exclusión/serialización para todas las futuras operaciones que muten estado.
- Definir una interfaz clara para que WPs posteriores ejecuten comandos bajo esa serialización sin acceder directamente al estado mutable desde rutas.
- Exponer un endpoint técnico estable `GET /api/v1/health` que permita comprobar que el proceso está vivo sin revelar datos institucionales ni mutar estado.
- Incorporar manejo base de errores internos necesario para que el runtime no convierta excepciones inesperadas en mutaciones parciales conocidas.
- Establecer organización inicial de paquetes backend para separar API, dominio/estado y servicios sin sobrediseñar capas aún vacías.

## Criterios de aceptación

1. **CA-001:** un backend recién iniciado está en `SIN_PREPARAR`, sin preparación, sesión, votación ni CSV activos.
2. Reiniciar el proceso crea una instancia nueva del estado; no intenta leer ni reconstruir una ejecución anterior.
3. Existe una sola instancia de estado operativo por proceso y las rutas/servicios no crean copias independientes.
4. Toda futura mutación puede canalizarse por una abstracción única de ejecución serializada.
5. Dos tareas de prueba que intenten mutar una variable sintética mediante esa abstracción se ejecutan en un orden exclusivo y determinable, sin carreras sobre la sección crítica.
6. `GET /api/v1/health` responde correctamente y no modifica estado.
7. No existe lógica funcional de preparación/sesión/votación anticipada.
8. El backend sigue siendo compatible con ejecución productiva de un único worker; este WP no introduce mecanismos que presupongan múltiples procesos compartiendo memoria.

## Pruebas obligatorias

- Unitarias del estado inicial.
- Tests del `lifespan` que comprueben creación y descarte de recursos.
- Test de concurrencia de la abstracción de serialización usando tareas concurrentes sintéticas.
- Test HTTP del endpoint `/api/v1/health` mediante HTTPX/AnyIO.
- Ruff, Pyright y pytest verdes para el alcance.

## Invariantes y restricciones

- Estado exclusivamente en memoria.
- Sin recuperación de sesión.
- Un único worker en producción.
- Las rutas no deben contener reglas de negocio.
- No incorporar Redis, base de datos, colas externas o locks multiproceso.
- No agregar dependencias directas nuevas fuera del stack aprobado sin escalamiento.
- No definir todavía DTOs completos `ModerationState` o `PublicState`.

## Decisiones que requieren escalamiento

Escalar cualquier necesidad de:

- persistir el estado;
- usar más de un proceso/worker con estado compartido;
- cambiar el mecanismo global REST/API aprobado;
- agregar infraestructura externa para concurrencia;
- crear contratos de negocio no autorizados por este WP.
