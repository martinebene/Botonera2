# WP-004 - Motor de auditoría CSV seguro

## Estado documental

`APROBADO`

## Objetivo

Implementar un motor de auditoría institucional independiente de las reglas de negocio, capaz de crear, escribir, sincronizar y cerrar los tres CSV jerárquicos de una preparación/sesión de forma segura y testeable.

## Resultado esperado

Existe un componente backend que puede abrir un conjunto de archivos L1/L2/L3, registrar eventos con secuencia monotónica y jerarquía acumulativa, ejecutar `flush` + `fsync` antes de confirmar una escritura y quedar definitivamente cerrado al finalizar.

La integración con `Preparar sala`, votaciones y demás eventos de negocio corresponde a WPs posteriores.

## Dependencias

- WP-001 integrado.
- DT-011 y DT-012 cerradas.

## Alcance

- Implementar un componente de auditoría que reciba un directorio base y una fecha/hora local real de inicio.
- Crear la carpeta diaria necesaria.
- Crear tres archivos con base canónica:

```text
AAAA-MM-DD_HH-MM-SS-L1.csv
AAAA-MM-DD_HH-MM-SS-L2.csv
AAAA-MM-DD_HH-MM-SS-L3.csv
```

- Nunca sobrescribir archivos existentes.
- Si excepcionalmente ya existe un conjunto con la marca correspondiente al segundo real de inicio, avanzar **solo la marca utilizada para el nombre** al segundo siguiente; si también existe, continuar segundo a segundo hasta el primer nombre libre.
- No usar sufijos `-02`, `-03` ni similares.
- Si el segundo nominal libre cruza a otra fecha, utilizar la carpeta correspondiente a esa fecha nominal para que carpeta y nombre sean coherentes.
- La marca nominal del nombre no modifica la hora real de la preparación ni los timestamps de los eventos.
- Escribir encabezado canónico:

```text
seq;timestamp;level;tag;event_code;message
```

- Codificación UTF-8 con BOM y delimitador `;`.
- Timestamp de cada evento en hora local real del servidor con formato `AAAA-MM-DD HH:MM:SS`.
- Mantener una secuencia `seq` monotónica por conjunto; las copias del mismo evento en varios niveles conservan el mismo `seq`.
- Implementar jerarquía acumulativa:
  - evento L1 → archivo L1;
  - evento L2 → archivos L1 y L2;
  - evento L3 → archivos L1, L2 y L3.
- Para cada evento, completar escritura en todos los archivos destino, `flush` y `fsync` antes de retornar éxito.
- Si falla una escritura/sincronización requerida:
  - devolver/elevar un error técnico inequívoco;
  - marcar el escritor como no confiable/fallado para impedir falsas confirmaciones posteriores;
  - no afirmar que el evento quedó auditado completamente.
- Implementar cierre explícito del conjunto. Después de cerrar, cualquier intento de registrar eventos debe rechazarse sin modificar archivos.
- Permitir que el llamador registre el evento final antes de invocar el cierre; el motor no inventa por sí mismo semántica de cancelación/cierre.
- Mantener la implementación apta para ser utilizada bajo el serializador global de WP-002, sin introducir un segundo mecanismo de orden de negocio.

## Fuera de alcance

- Ejecutar `Preparar sala` o cambiar estado global.
- Decidir qué evento de negocio es L1/L2/L3; los WPs propietarios definirán su nivel y código.
- Mantener buffer histórico para frontend.
- Restaurar estado desde CSV.
- Editar/reabrir archivos cerrados.
- Backup externo.
- Rotación por tamaño o compresión.
- Base de datos.

## Criterios de aceptación

1. **CA-053:** cada apertura produce un conjunto diferente y nunca sobrescribe archivos existentes.
2. Si se simulan dos aperturas con la misma hora real al segundo, la segunda utiliza en sus nombres el primer segundo posterior libre, sin sufijos; los timestamps de eventos siguen usando la hora real suministrada a cada evento.
3. **CA-054:** L1 aparece solo en CSV1; L2 aparece en CSV1+CSV2; L3 aparece en CSV1+CSV2+CSV3.
4. Todas las filas cumplen `seq;timestamp;level;tag;event_code;message`, `;` y UTF-8 con BOM.
5. La secuencia es monotónica dentro del conjunto y el mismo evento conserva el mismo `seq` en sus archivos destino.
6. **CA-055, componente técnico:** una llamada exitosa no retorna hasta que se ejecutaron escritura, `flush` y `fsync` en todos los archivos requeridos.
7. Un fallo simulado de escritura/fsync no se informa como éxito y deja al escritor en estado de fallo cerrado para nuevas escrituras.
8. **CA-056, componente técnico:** después de `close`, nuevos intentos de escritura fallan y no alteran los archivos.
9. El motor no intenta reconstruir estado ni abrir/modificar conjuntos históricos por sí mismo.
10. Los archivos pueden abrirse correctamente con herramientas CSV comunes y contienen mensajes humanos legibles.

## Pruebas obligatorias

- Tests con directorio temporal para creación de carpeta/archivos/encabezados.
- Test de cada nivel acumulativo L1/L2/L3.
- Test de secuencia compartida entre archivos.
- Test de UTF-8 con BOM y caracteres acentuados.
- Test de colisión con misma fecha/hora real simulada: el segundo conjunto usa `+1 s` nominal; si ese nombre también está ocupado, usa `+2 s`, etc.; nunca sobrescribe ni agrega sufijo.
- Test que demuestre que el ajuste nominal del nombre no altera timestamps internos reales.
- Test de cambio de fecha nominal al resolver una colisión en `23:59:59`.
- Tests con mocks/fakes de `flush`/`fsync` verificando invocación antes del retorno exitoso.
- Test de error de escritura o `fsync` y estado posterior de fallo cerrado.
- Test de cierre irreversible del writer.
- Ruff, Pyright y pytest verdes.

## Invariantes y restricciones

- Hora real local del servidor para eventos; precisión a segundos.
- La hora nominal del nombre solo puede separarse de la real para evitar una colisión de archivos existente.
- `flush` + `fsync` obligatorios.
- Los tres CSV siguen siendo el registro institucional, no una base de datos.
- No reabrir/reparar archivos cerrados o de una ejecución previa.
- No agregar buffering que permita confirmar una operación antes de persistir el evento correspondiente.
- No cambiar columnas, delimitador, codificación o jerarquía sin escalamiento.

## Decisiones que requieren escalamiento

Escalar cualquier necesidad de:

- cambiar columnas o formato;
- sustituir la regla aprobada de primer segundo nominal libre;
- eliminar `fsync` por rendimiento;
- usar logging asíncrono/bufferizado para eventos institucionales;
- incorporar base de datos o journal alternativo;
- cambiar la jerarquía L1/L2/L3.
