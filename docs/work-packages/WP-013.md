# WP-013 - Finalización inconclusa, pérdida de quórum y cierre de sesión con votación pendiente

## Estado documental

`APROBADO`

## Objetivo

Implementar los flujos que finalizan una votación sin consolidar un resultado ordinario: finalización manual anticipada desde Moderación, pérdida automática de quórum durante una recepción `EN_CURSO` y resolución de una votación pendiente al cerrar la sesión.

El resultado final de esos flujos es `INCONCLUSA`, siempre sobre la misma instancia `Votacion`, conservando votos y trazabilidad, respetando DEC-010 y el contrato REST/fallo cerrado de DEC-011.

Este WP también reemplaza el rechazo transitorio de cierre de sesión con votación pendiente que existía desde WP-008: `DELETE /api/v1/sesion` debe resolver primero una `EN_CURSO` o `EMPATADA` conforme a las reglas aprobadas y luego continuar el cierre de sesión.

## Resultado esperado

Al integrar este WP deben quedar disponibles estos recorridos:

### Finalización manual

```text
POST /api/v1/votaciones/{id}/finalizacion
{ "motivo": "..." }
```

sobre una votación activa:

```text
EN_CURSO + resultado=None
    -> CERRADA + resultado=INCONCLUSA
    -> votacion_activa=None
```

con motivo obligatorio persistido y conservado en la entidad.

### Pérdida de quórum

Una presencia aceptada que deje el cuerpo por debajo del quórum durante `EN_CURSO` debe producir inmediatamente:

```text
EN_CURSO + resultado=None
    -> CERRADA + resultado=INCONCLUSA
    -> votacion_activa=None
```

sin calcular mayoría ordinaria y sin revertir la presencia que causó la pérdida.

### Cierre de sesión con `EN_CURSO`

```text
DELETE /api/v1/sesion
```

debe, dentro de la misma adquisición del serializador:

```text
EN_CURSO + None
    -> CERRADA + INCONCLUSA
    -> liberar votacion_activa
    -> cerrar sesión
    -> SIN_PREPARAR
```

### Cierre de sesión con `EMPATADA`

Debe transformar la misma instancia:

```text
CERRADA + EMPATADA
    -> CERRADA + INCONCLUSA
    -> liberar votacion_activa
    -> cerrar sesión
    -> SIN_PREPARAR
```

conservando la fecha/hora de cierre normal y la auditoría previa del empate.

## Alcance

### 1. Transición de dominio a `INCONCLUSA`

La entidad `Votacion` debe encapsular las transiciones autorizadas por este WP y protegerlas contra usos internos inválidos.

Desde una recepción abierta:

```text
estado = EN_CURSO
resultado = None
```

una finalización inconclusa debe dejar:

```text
estado = CERRADA
resultado = INCONCLUSA
fecha_hora_cierre = instante de finalización
```

conservando:

- id;
- número;
- tipo;
- tema;
- tipo de mayoría;
- factor;
- base;
- fecha/hora de apertura;
- todos los votos ordinarios ya emitidos.

La transición debe liberar `EstadoOperativo.votacion_activa` solamente después de persistir y aplicar el hecho institucional.

La misma entidad permanece en `Sesion.votaciones`.

### 2. `INCONCLUSA` es irreversible

Una votación con resultado `INCONCLUSA`:

- permanece `CERRADA`;
- no vuelve a `EN_CURSO`;
- no acepta votos;
- no recalcula mayoría SIMPLE ni ESPECIAL;
- no puede pasar a `EMPATADA`;
- no admite desempate presidencial;
- no cambia si después se recupera quórum;
- no vuelve a ocupar `votacion_activa`.

El dominio debe rechazar una segunda finalización o cualquier intento de reabrir/recalcular por helpers de este alcance.

### 3. Motivo de finalización manual

La entidad debe representar el motivo manual cuando corresponda.

Reglas:

- inicialmente es `None`;
- una finalización manual válida lo fija al texto normalizado;
- queda inmutable después;
- una pérdida de quórum no inventa motivo manual;
- una finalización derivada del cierre de sesión no inventa motivo manual;
- un cierre normal por completitud no asigna motivo manual.

No debe utilizarse el campo manual para almacenar códigos internos como `PERDIDA_QUORUM` o `CIERRE_SESION`.

### 4. Endpoint de finalización manual

Implementar exactamente:

```text
POST /api/v1/votaciones/{id}/finalizacion
```

Body:

```json
{
  "motivo": "Texto obligatorio"
}
```

Respuesta exitosa:

```text
204 No Content
```

El body debe:

- prohibir campos extra;
- aceptar solo string estricto;
- aplicar `strip`;
- rechazar vacío/blancos con `422`;
- no aceptar `null`, números, booleanos, listas u objetos como motivo.

No se agrega un segundo endpoint alternativo de finalización.

### 5. Protección contra comando obsoleto mediante `{id}`

Bajo el `EjecutorMutaciones`, antes de finalizar manualmente debe verificarse en orden determinista:

1. estado global `SESION_ABIERTA`;
2. existencia de votación activa compatible;
3. coincidencia exacta entre `{id}` y `votacion_activa.id`;
4. `estado=EN_CURSO`;
5. `resultado=None`.

Un id atrasado nunca debe aplicarse a una nueva votación que haya reemplazado a la observada por la UI.

Errores funcionales mínimos:

```text
ESTADO_INCOMPATIBLE
VOTACION_NO_COINCIDE
VOTACION_NO_EN_CURSO
```

con HTTP `409 Conflict` y la forma de error estable del backend.

Los rechazos que alcancen el servicio con auditoría activa deben persistirse L2 antes de devolver el conflicto.

### 6. Finalización manual no calcula mayoría

Una finalización manual válida durante `EN_CURSO` siempre produce `INCONCLUSA`.

No importa:

- cuántos votos existan;
- si existen cero votos;
- qué tipo de mayoría fue configurado;
- qué factor/base tenga la votación.

No debe llamar al cálculo ordinario de WP-011 ni generar `APROBADA`, `RECHAZADA` o `EMPATADA`.

Si el último voto normal ganó antes la carrera y ya resolvió la votación, el comando manual que entre después debe observar el estado actualizado y rechazarse, no modificar el resultado final.

### 7. Pérdida automática de quórum durante `EN_CURSO`

La tecla `9` continúa siendo la única fuente de presencia.

Después de auditar y aplicar una presencia aceptada en `SESION_ABIERTA`, si existe una votación activa `EN_CURSO + resultado=None`, el flujo debe evaluar primero:

```text
quorum_alcanzado()
```

Si es falso:

- persistir la finalización inconclusa con causa `PERDIDA_QUORUM`;
- aplicar `CERRADA + INCONCLUSA` sobre la misma instancia;
- fijar fecha/hora de cierre;
- conservar votos;
- no calcular mayoría;
- liberar `votacion_activa`;
- devolver la respuesta de presencia solamente si toda la secuencia institucional obligatoria pudo completarse.

### 8. Prioridad `PERDIDA_QUORUM` sobre autocierre normal

Después de un cambio de presencia en `EN_CURSO` el orden obligatorio es:

```text
1. evaluar pérdida de quórum
2. solo si aún hay quórum, evaluar completitud
```

Caso crítico:

- había un presente sin votar;
- ese concejal se retira;
- los restantes ya habían votado;
- la retirada deja además presentes por debajo del quórum.

Resultado requerido:

```text
INCONCLUSA
```

No debe autocerrar y calcular mayoría ordinaria.

Debe existir una prueba específica que detecte una inversión accidental de esta prioridad.

### 9. Pérdida de quórum sin votación

La regla existente se conserva:

- la sesión permanece `SESION_ABIERTA`;
- no se crea ninguna votación ni resultado;
- abrir una nueva votación queda impedido por quórum insuficiente;
- recuperar quórum vuelve a habilitar la apertura conforme a precondiciones normales.

WP-013 no debe cerrar la sesión por pérdida de quórum.

### 10. Pérdida de quórum después de `EMPATADA`

Si `votacion_activa` apunta a una votación:

```text
estado=CERRADA
resultado=EMPATADA
```

una presencia que provoque pérdida de quórum:

- se procesa normalmente como cambio de presencia;
- NO cambia la votación;
- NO produce `INCONCLUSA`;
- NO libera `votacion_activa`;
- NO modifica fecha de cierre;
- NO altera votos;
- NO bloquea el futuro flujo de desempate por esa sola pérdida.

### 11. Cierre de sesión con votación `EN_CURSO`

`DELETE /api/v1/sesion` conserva su contrato sin body.

Dentro de la misma adquisición del `EjecutorMutaciones`, si encuentra `EN_CURSO + None`:

1. validar sesión;
2. persistir L3 `VOTACION_FINALIZADA_INCONCLUSA` con causa `CIERRE_SESION`;
3. aplicar `CERRADA + INCONCLUSA` y fecha de cierre;
4. conservar votos;
5. liberar `votacion_activa`;
6. persistir `SESION_CERRADA`;
7. ejecutar `escritor.cerrar()`;
8. limpiar estado y volver a `SIN_PREPARAR` solo si el cierre físico terminó correctamente.

No se exige motivo manual al cliente.

### 12. Cierre de sesión con `EMPATADA`

Si `DELETE /api/v1/sesion` encuentra la misma instancia en:

```text
CERRADA + EMPATADA
```

la transición autorizada es:

```text
CERRADA + EMPATADA
    -> CERRADA + INCONCLUSA
```

Debe:

- persistir primero el evento de finalización inconclusa con causa `CIERRE_SESION`;
- conservar la `fecha_hora_cierre` original;
- conservar votos ordinarios;
- conservar en CSV el evento previo de empate;
- no crear voto presidencial;
- no modificar conteos;
- liberar `votacion_activa`;
- continuar después con el cierre normal de sesión.

La entidad debe permitir específicamente esta transición solo para el flujo autorizado de cierre de sesión, sin convertir `EMPATADA` en un resultado libremente editable.

### 13. Cierre de sesión sin votación pendiente

La ruta ya integrada debe seguir funcionando sin cambios funcionales cuando:

```text
votacion_activa = None
```

No se generan eventos ficticios de votación.

### 14. `CERRADA + resultado=None` técnico no se recupera

El estado:

```text
CERRADA + resultado=None
```

que pueda quedar por fallo previo de auditoría no se transforma en un nuevo flujo de negocio.

WP-013 no agrega:

- reparación;
- recalculo;
- finalización manual de ese estado;
- reanudación del writer;
- endpoint de recovery.

El fallo cerrado vigente continúa prevaleciendo.

### 15. Auditoría de `INCONCLUSA`

Antes de aplicar cualquiera de las mutaciones de votación de este WP debe persistirse un evento L3 estable:

```text
VOTACION_FINALIZADA_INCONCLUSA
```

El mensaje debe incluir como mínimo:

- número de votación;
- id técnico;
- causa;
- estado previo;
- resultado previo si existe;
- cantidad total de votos ordinarios conservados;
- resultado nuevo `INCONCLUSA`.

Por causa:

#### `MANUAL`

Agregar:

- motivo manual normalizado.

#### `PERDIDA_QUORUM`

Agregar:

- cantidad de presentes después del cambio;
- quórum configurado/requerido.

#### `CIERRE_SESION`

Agregar:

- indicación explícita de cierre de sesión;
- si provenía de `EMPATADA`, registrar inequívocamente ese resultado previo.

Un único evento institucional puede representar la finalización y su resultado `INCONCLUSA`; no se requiere duplicar el mismo hecho con un segundo evento redundante.

### 16. Auditoría de rechazos manuales

Los rechazos funcionales de `POST /votaciones/{id}/finalizacion` que llegan al servicio mientras existe contexto auditable deben registrar L2, con un `event_code` estable y un mensaje que identifique:

- operación;
- id solicitado cuando corresponda;
- código estable del rechazo.

Si ese registro L2 falla, prevalece `AUDITORIA_NO_DISPONIBLE` y no se devuelve un conflicto normal como si la auditoría siguiera saludable.

### 17. Fallo cerrado de finalización manual

Secuencia:

```text
VALIDAR
-> AUDITAR INCONCLUSA
-> MUTAR
-> LIBERAR
```

Si falla el evento L3:

- sigue `EN_CURSO + None`;
- conserva votos;
- no fija fecha de cierre;
- no fija motivo manual;
- mantiene `votacion_activa`;
- writer en fallo cerrado;
- API `503 AUDITORIA_NO_DISPONIBLE`.

### 18. Fallo cerrado de pérdida de quórum

La presencia que provoca pérdida de quórum es un hecho previo independiente.

Si la presencia ya fue auditada y aplicada pero falla el evento de `INCONCLUSA`:

- NO revertir presencia;
- mantener votación `EN_CURSO + None`;
- no fijar fecha de cierre;
- mantener `votacion_activa`;
- writer en fallo cerrado;
- la pulsación no se informa como éxito técnico.

Debe existir una prueba que confirme el último estado persistido, no solo la excepción.

### 19. Fallo cerrado de cierre de sesión

#### Falla la finalización de votación

Si falla `VOTACION_FINALIZADA_INCONCLUSA`:

- no mutar votación;
- no liberar referencia;
- no intentar confirmar cierre de sesión;
- no limpiar estado.

#### Finalización de votación exitosa, falla `SESION_CERRADA`

Debe quedar:

- votación final `INCONCLUSA` en historial;
- `votacion_activa=None`;
- sesión todavía en memoria/`SESION_ABIERTA`;
- writer en fallo cerrado;
- sin éxito técnico.

No se revierte un hecho de votación ya persistido.

#### `SESION_CERRADA` persistido, falla cierre físico del writer

Conservar exactamente la semántica existente de DEC-008: no limpiar el contexto ni confirmar cierre funcional.

### 20. Concurrencia

Todos los recorridos deben reutilizar el mismo `EjecutorMutaciones`.

No agregar:

- segundo ejecutor;
- `asyncio.Lock` adicional;
- `threading.Lock`;
- workers;
- colas;
- background tasks.

Pruebas concurrentes obligatorias:

1. finalización manual vs. último voto;
2. finalización manual vs. cambio de presencia que pierde quórum;
3. cierre de sesión vs. último voto;
4. cierre de sesión vs. presencia;
5. cierre de sesión vs. finalización manual;
6. comando manual con id de una votación anterior mientras una nueva ya es activa.

Las pruebas deben encolar realmente operaciones sobre el serializador compartido y verificar el estado observado por la segunda operación.

### 21. Semántica de carreras

No se prescribe cuál intención humana “debe ganar” independientemente del orden.

La regla es:

```text
primera adquisición del EjecutorMutaciones
    -> completa su transición
segunda adquisición
    -> evalúa el estado ya actualizado
```

Ejemplos:

- si finalización manual entra antes del último voto, queda `INCONCLUSA` y el voto posterior se rechaza;
- si el último voto cierra/calcula antes, la finalización manual posterior no altera el resultado;
- si cierre de sesión entra primero, resuelve/descarta el contexto antes de que el comando posterior evalúe;
- un `{id}` obsoleto jamás se aplica a otra votación.

### 22. Contrato HTTP y OpenAPI

Debe actualizarse OpenAPI con:

```text
POST /api/v1/votaciones/{id}/finalizacion
```

incluyendo body y respuestas documentadas.

Mapeo mínimo:

- `204`: finalización manual aplicada;
- `409 + ESTADO_INCOMPATIBLE`;
- `409 + VOTACION_NO_COINCIDE`;
- `409 + VOTACION_NO_EN_CURSO`;
- `422`: validación del transporte;
- `503 + AUDITORIA_NO_DISPONIBLE`;
- `500 + ERROR_INTERNO`.

`DELETE /api/v1/sesion` continúa sin body y con `204` exitoso, pero deja de responder `VOTACION_PENDIENTE` únicamente por encontrar `EN_CURSO` o `EMPATADA`: ahora debe resolver esos casos.

No eliminar `VOTACION_PENDIENTE` del vocabulario general donde siga siendo necesario para otros comandos como apertura de votación.

### 23. Reutilización interna sin crear autoridad paralela

La finalización inconclusa puede centralizarse en un helper/servicio común para evitar duplicar reglas entre:

- comando manual;
- entrada/presencia;
- cierre de sesión.

Pero debe mantenerse:

- una sola instancia `Votacion`;
- un solo `EstadoOperativo`;
- un solo escritor;
- un solo `EjecutorMutaciones`.

Un helper llamado desde una operación que ya posee el lock no debe readquirir el mismo ejecutor.

### 24. Compatibilidad con flujo ordinario integrado

Deben permanecer sin regresión:

- voto ordinario 1/2/3;
- voto único e irreversible;
- presencia 9;
- test 8;
- autocierre por completitud cuando se mantiene quórum;
- SIMPLE;
- ESPECIAL;
- `APROBADA`/`RECHAZADA` liberan activa;
- `EMPATADA` mantiene activa;
- apertura bloqueada por `EMPATADA`;
- pérdida de quórum posterior a `EMPATADA` no altera el empate;
- auditoría previa a cada mutación institucional;
- una única entidad en historial/estado.

## Criterios de aceptación específicos del WP

1. Existe `POST /api/v1/votaciones/{id}/finalizacion` y responde `204` en éxito.
2. Motivo manual válido se normaliza con `strip`.
3. Motivo vacío/blancos se rechaza `422`.
4. `null`, booleano, número, lista u objeto como motivo se rechazan `422`.
5. Campos extra del body se rechazan `422`.
6. Finalización manual con cero votos produce `CERRADA + INCONCLUSA`.
7. Finalización manual con votos parciales conserva exactamente esos votos.
8. Finalización manual no calcula SIMPLE ni ESPECIAL.
9. Motivo manual queda disponible en la misma entidad histórica.
10. Finalización manual libera `votacion_activa`.
11. La instancia histórica es la misma que estaba activa.
12. Id incorrecto no afecta la votación actual y devuelve `VOTACION_NO_COINCIDE`.
13. Sin sesión compatible se devuelve `ESTADO_INCOMPATIBLE`.
14. Sin votación manualmente finalizable se devuelve `VOTACION_NO_EN_CURSO`.
15. Una finalización repetida no altera `INCONCLUSA`.
16. Recuperar quórum no reabre una `INCONCLUSA`.
17. Presencia que pierde quórum durante `EN_CURSO` produce inmediatamente `INCONCLUSA`.
18. Los votos previos sobreviven a pérdida de quórum.
19. Pérdida de quórum fija fecha/hora de cierre.
20. Pérdida de quórum no asigna motivo manual.
21. Pérdida de quórum libera `votacion_activa`.
22. Pérdida de quórum prevalece sobre completitud si ambas aparecen en la misma retirada.
23. Con quórum conservado, la retirada que completa sigue ejecutando autocierre ordinario.
24. Pérdida de quórum sin votación no cierra la sesión.
25. Recuperar quórum sin votación vuelve a permitir apertura conforme a reglas existentes.
26. Pérdida de quórum posterior a `EMPATADA` no altera el empate.
27. `DELETE /sesion` con `EN_CURSO` la transforma primero a `INCONCLUSA` y luego cierra sesión.
28. Cierre de sesión con `EN_CURSO` conserva votos parciales.
29. Cierre de sesión con `EN_CURSO` no exige body/motivo manual.
30. `DELETE /sesion` con `EMPATADA` cambia esa misma instancia a `INCONCLUSA`.
31. Cierre de sesión con `EMPATADA` conserva fecha/hora de cierre original.
32. El evento previo `EMPATADA` permanece en auditoría.
33. Cierre de sesión con `EMPATADA` no crea voto presidencial.
34. Cierre de sesión sin votación pendiente conserva comportamiento previo.
35. Finalización inconclusa se audita antes de mutar.
36. Evento manual contiene motivo.
37. Evento de pérdida de quórum contiene presentes y quórum requerido.
38. Evento por cierre de sesión contiene causa y resultado previo cuando era `EMPATADA`.
39. Fallo de auditoría manual deja `EN_CURSO + None`.
40. Fallo de auditoría derivado de pérdida de quórum conserva la presencia ya aplicada pero no finaliza la votación.
41. Fallo de finalización dentro de cierre de sesión deja la votación previa y sesión abiertas.
42. Si `INCONCLUSA` ya fue persistida/aplicada y luego falla `SESION_CERRADA`, no se revierte la votación.
43. Writer fallado bloquea nuevas mutaciones conforme al mecanismo existente.
44. Finalización manual vs. último voto respeta orden real del serializador.
45. Cierre de sesión vs. último voto respeta orden real del serializador.
46. Finalización manual vs. pérdida de quórum respeta orden real del serializador.
47. Cierre de sesión vs. finalización manual respeta orden real del serializador.
48. Un id obsoleto no finaliza una votación nueva.
49. No existe segundo lock/ejecutor.
50. `CERRADA + resultado=None` técnico no obtiene recovery nuevo.
51. Ningún flujo de este WP modifica un resultado `APROBADA` o `RECHAZADA` ya final.
52. Ningún flujo automático por pérdida de quórum modifica una `EMPATADA`.
53. OpenAPI refleja el nuevo endpoint y conserva `DELETE /sesion` sin body.
54. Los checks globales permanecen verdes.

## Pruebas mínimas a versionar

### Dominio

- transición `EN_CURSO + None -> CERRADA + INCONCLUSA`;
- preservación de votos/datos constitutivos;
- motivo manual único e inmutable;
- ausencia de motivo manual para causas derivadas;
- rechazo de doble finalización;
- rechazo de transición inválida desde resultados finales;
- `EMPATADA -> INCONCLUSA` únicamente por primitive interna autorizada para cierre de sesión;
- preservación de fecha de cierre en esa transición.

### Servicio/API de votación

- finalización manual cero votos;
- votos parciales;
- body válido/normalizado;
- todos los 422 relevantes;
- id correcto/incorrecto;
- sin sesión;
- sin activa;
- activa no `EN_CURSO`;
- auditoría L3 y rechazo L2;
- fallo cerrado 503.

### Entrada/presencia

- pérdida de quórum automática;
- votos conservados;
- prioridad sobre completitud;
- completitud normal si todavía existe quórum;
- sesión sin votación;
- `EMPATADA` no modificada;
- fallo posterior al evento de presencia sin rollback de presencia.

### Sesión

- cierre sin votación;
- cierre con `EN_CURSO`;
- cierre con `EMPATADA`;
- secuencia de eventos;
- fallo en finalización de votación;
- fallo de `SESION_CERRADA` después de `INCONCLUSA`;
- fallo físico de writer conserva semántica integrada.

### Concurrencia

Tests que bloqueen/encolen realmente sobre el mismo `EjecutorMutaciones` para las carreras descritas en el alcance.

No basta con nombres de tests que digan “concurrente”: deben demostrar el orden de adquisición y el estado observado por la operación posterior.

## Componentes previsiblemente afectados

Orientativamente:

- dominio de `Votacion`;
- servicio de votación;
- servicio de entrada/presencia;
- servicio de sesión;
- rutas/esquemas API de votaciones;
- mapeo de errores API/dominio;
- tests backend de votaciones, entrada, sesión, API y concurrencia;
- documentación propietaria del comportamiento implementado.

Esta lista no autoriza expansión incidental de alcance.

## Fuera de alcance

No implementar incidentalmente:

- desempate presidencial ni voto de Presidencia;
- resolución manual de `EMPATADA` fuera del cierre de sesión;
- finalización manual de `CERRADA + resultado=None` técnico;
- recovery del writer/estado;
- reapertura de `INCONCLUSA`;
- edición/borrado de votos;
- uso de palabra;
- advertencias frontend por palabra pendiente;
- Orden del Día;
- SSE;
- snapshots `ModerationState`/`PublicState`;
- frontend de Moderación;
- frontend de Recinto;
- bridge físico;
- remapeo;
- base de datos;
- recuperación después de reinicio.

El desempate presidencial permanece reservado al alcance posterior correspondiente.

## Restricciones técnicas

- Python 3.14.
- FastAPI/Pydantic según stack congelado.
- Un solo proceso/worker en producción.
- Un único `EstadoOperativo`.
- Un único `EjecutorMutaciones`.
- Auditoría síncrona con `flush`/`fsync` antes de mutaciones institucionales.
- Sin nuevas dependencias salvo necesidad real y decisión autorizada.
- Sin base de datos.
- Sin relectura de configuración/padrón para resolver reglas activas.

Todos los checks aplicables deben quedar verdes tanto antes como después de incorporar cualquier avance legítimo de `origin/main`.

## Sincronización y entrega

El implementador debe:

1. trabajar únicamente en el worktree/rama Orca asignado;
2. no modificar `PLAN.md` ni el estado documental del WP;
3. crear commits normales, sin rebase ni force-push;
4. antes del candidato final, `git fetch origin` y comparar con `origin/main`;
5. si `main` avanzó, incorporar mediante merge normal, no rebase;
6. repetir todos los checks después de ese merge;
7. push normal de la rama;
8. abrir/actualizar PR contra `main`;
9. identificar SHA remoto exacto del candidato;
10. esperar CI correspondiente a ese SHA;
11. dejar worktree/rama preservados para revisión independiente;
12. no hacer merge.

## Criterio de finalización del implementador

La implementación solo se considera candidata a revisión cuando existe:

- alcance completo;
- tests versionados;
- documentación propietaria alineada;
- checks globales verdes;
- estado Git limpio;
- commits normales;
- rama remota;
- PR contra `main`;
- SHA candidato exacto;
- CI aplicable verde;
- informe final exhaustivo;
- ningún merge realizado.

## Criterio de integración

No integrar mientras exista:

- algún hallazgo `BLOQUEANTE`;
- algún hallazgo `IMPORTANTE`;
- CI aplicable fallida;
- discrepancia entre SHA revisado y SHA candidato de la PR;
- expansión de alcance no autorizada.

Los hallazgos `MENOR` pueden evaluarse individualmente por el orquestador/humano sin bloquear automáticamente, siempre que no oculten un defecto funcional, de auditoría o concurrencia.
