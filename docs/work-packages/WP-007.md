# WP-007 - Simulador CLI reproducible de dispositivos y escenarios de entrada

## Estado documental

`APROBADO`

Un WP no puede pasar a `EN_CURSO` en `PLAN.md` mientras no esté `APROBADO`.

## Objetivo

Implementar en `tools/device-simulator/` una herramienta de desarrollo **CLI**, reproducible y sin hardware físico que envíe pulsaciones lógicas reales al backend mediante `POST /api/v1/entradas/tecla`.

El simulador debe servir simultáneamente para:

- uso manual rápido por una persona desde terminal;
- diagnóstico de respuestas reales del backend;
- emisión de cualquier tecla que pueda resultar relevante para un teclado numérico, incluidas teclas sin semántica funcional en el estado actual;
- ejecución repetible de secuencias y grupos concurrentes de pulsaciones;
- automatización de expectativas básicas sin convertir al simulador en una segunda implementación de las reglas de negocio.

El simulador **no decide** si una tecla es válida, habilitada o produce un efecto. Su responsabilidad termina en construir una pulsación lógica, enviarla al backend y mostrar/evaluar la respuesta. La autoridad funcional continúa siendo exclusivamente FastAPI.

## Resultado esperado

Al completar WP-007 debe existir una CLI utilizable desde el checkout del repositorio que permita tres formas de uso:

1. **modo interactivo manual**, manteniendo una consola abierta y aceptando entradas simples como `5-1`, `5-9`, `12-8`, `3-+` o `7-enter`;
2. **pulsación única desde shell**, utilizando la misma sintaxis compacta y terminando después de una respuesta;
3. **escenario declarativo**, leído desde JSON versionable, capaz de ejecutar pulsaciones secuenciales, pausas y grupos concurrentes, con expectativas opcionales sobre la respuesta.

Cada envío debe mostrar:

- qué pulsación lógica fue enviada;
- el status HTTP recibido;
- el **body literal devuelto por el servidor**, sin reconstruirlo, resumirlo ni volver a serializarlo antes de mostrarlo;
- adicionalmente puede mostrarse una línea resumen para lectura rápida cuando la respuesta coincide con el DTO conocido.

La salida literal es obligatoria para que la herramienta sea útil al depurar contratos, rechazos y errores inesperados.

## Alcance

### 1. Implementar la CLI en `tools/device-simulator/`

La herramienta debe residir en la ubicación ya reservada por WP-001/DT-024:

```text
tools/device-simulator/
```

Debe ser Python 3.14 y ejecutarse mediante el entorno `uv` del repositorio.

Puede reutilizar `httpx` y `anyio`, ya disponibles en el grupo de desarrollo del repositorio. WP-007 no debe agregar una nueva dependencia de terceros si las capacidades existentes son suficientes.

La organización interna concreta de módulos/archivos pertenece a la autonomía local del implementador, siempre que la invocación para una persona siga siendo simple y quede documentada en `tools/device-simulator/README.md`.

### 2. Endpoint único de pulsaciones

Todas las pulsaciones del simulador se envían exclusivamente a:

```text
POST /api/v1/entradas/tecla
```

con body:

```json
{
  "dispositivo": "dev05",
  "tecla": "9"
}
```

No debe importar ni invocar directamente servicios, modelos, funciones o estado interno de `apps/backend` para producir el efecto funcional.

El uso del endpoint HTTP real es parte del propósito del simulador: debe ejercitar el mismo límite de integración que posteriormente utilizará el `device-bridge`.

### 3. URL del backend

La CLI debe aceptar una URL base configurable por argumento.

Debe existir un valor local cómodo por defecto:

```text
http://127.0.0.1:8000
```

La URL base y el path canónico deben componerse de forma segura, evitando duplicaciones accidentales de `/`.

No se versionan URLs privadas, tokens, credenciales ni configuración personal.

### 4. Sintaxis manual compacta

La entrada humana principal tiene la forma:

```text
<numero-dispositivo>-<tecla>
```

Ejemplos:

```text
5-1
5-9
12-8
3-+
8-.
4-enter
5--
```

Reglas:

- el separador es el **primer** guion `-` encontrado;
- la parte izquierda debe ser un número entero no negativo escrito sin el prefijo `dev`;
- el simulador lo convierte a `devNN` con al menos dos dígitos: `5 -> dev05`, `12 -> dev12`, `99 -> dev99`;
- la parte derecha debe ser texto no vacío y representa la tecla;
- por usar solo el primer guion como separador, `5--` representa correctamente el dispositivo `dev05` y la tecla literal `-`;
- no debe exigirse que el número pertenezca al padrón: `99-9`, por ejemplo, debe poder enviarse para ejercitar `DISPOSITIVO_NO_ASIGNADO`;
- no debe exigirse que la tecla tenga semántica conocida por el backend.

La consola debe aceptar de forma natural, como mínimo, números `0..9`, operadores y signos habituales (`.`, `/`, `*`, `-`, `+`) y nombres legibles para teclas no representables cómodamente por un carácter, por ejemplo `enter` y `numlock`.

**Regla crítica de diagnóstico:** el simulador no debe filtrar la entrada a `1`, `2`, `3`, `7`, `8` y `9`. Cualquier `tecla` textual no vacía debe poder llegar al backend. Esto permite probar teclas físicas sin semántica actual y entradas futuras/no contempladas; el backend es quien debe aceptarlas o rechazarlas.

Los aliases/conveniencias que se documenten para teclas físicas no constituyen todavía el contrato de normalización HID del `device-bridge`; ese contrato pertenece a WP-019. El simulador debe conservar la posibilidad de enviar explícitamente el string de tecla requerido por un escenario.

### 5. Modo interactivo manual

Ejecutar la CLI sin una pulsación ni un escenario debe abrir una consola interactiva persistente.

Comportamiento mínimo:

```text
> 1-9
[envio] dispositivo=dev01 tecla=9
[respuesta] HTTP 200
{"aceptada":true,"motivo":"PRESENCIA_ACTUALIZADA",...}

> 3-4
[envio] dispositivo=dev03 tecla=4
[respuesta] HTTP 200
{"aceptada":false,"motivo":"TECLA_NO_HABILITADA",...}
```

Después de cada comando válido debe quedar listo para recibir el siguiente sin reiniciar el proceso.

Debe incluir comandos internos simples y documentados al menos para:

- mostrar ayuda/sintaxis;
- mostrar la URL base efectiva;
- salir limpiamente de la consola.

Los nombres exactos de estos comandos internos pueden definirse localmente si son obvios y están documentados.

Un error de sintaxis manual no debe terminar la consola: debe explicar brevemente el formato esperado y permitir corregir el siguiente ingreso.

### 6. Pulsación única desde shell

La misma sintaxis compacta debe poder suministrarse como argumento al iniciar la herramienta.

Conceptualmente:

```text
uv run python tools/device-simulator/<entrada>.py 5-9
```

El nombre final del archivo ejecutable puede decidirlo el implementador, pero el README debe incluir el comando literal definitivo.

En este modo:

- se realiza exactamente un envío;
- se muestra la respuesta literal;
- el proceso termina con código `0` si hubo una respuesta HTTP válida, aunque esa respuesta represente un rechazo funcional normal `200`;
- errores de sintaxis, conexión, timeout o imposibilidad de obtener respuesta HTTP producen código distinto de cero.

Una respuesta HTTP `4xx/5xx` obtenida correctamente debe mostrarse íntegramente. La política de código de salida para `4xx/5xx` debe ser coherente y documentada; para automatización se prefiere código distinto de cero porque representa un fallo técnico/contractual y no un rechazo funcional normal del DTO `200`.

### 7. Respuesta literal obligatoria

Para **cada request HTTP efectivamente enviado** en modo manual, pulsación única o escenario, la salida debe incluir como mínimo:

```text
HTTP <status>
<body literal recibido>
```

El body debe provenir directamente del texto recibido del servidor (`response.text` o equivalente) y mostrarse sin:

- pretty-print JSON;
- ordenar campos;
- eliminar campos desconocidos;
- reemplazar el body por un DTO interno;
- ocultar el body porque el status sea de error.

Si el body está vacío, la salida debe dejarlo explícito de forma inequívoca.

Puede imprimirse además un resumen interpretado para comodidad humana, pero **nunca en sustitución** de la respuesta literal.

No es necesario imprimir todos los headers HTTP en la salida normal. El implementador puede agregar un modo de diagnóstico opcional si no amplía dependencias ni complejidad de forma relevante.

### 8. Errores de red y continuidad interactiva

Deben distinguirse claramente al menos:

- conexión rechazada/no disponible;
- timeout;
- error HTTP recibido del servidor;
- error de sintaxis local antes del envío.

En modo interactivo, un error de red o una respuesta HTTP de error no debe cerrar la consola; después del diagnóstico debe permitirse un nuevo comando.

No imprimir traceback completo al usuario por errores operativos esperables. Los errores inesperados sí deben producir un fallo visible y código no cero cuando el proceso termina.

### 9. Escenarios JSON reproducibles

El simulador debe ejecutar escenarios declarativos almacenados en JSON versionable.

El formato debe ser sencillo, explícito y documentado. Debe soportar como mínimo tres tipos de paso:

1. **pulsación**;
2. **pausa**;
3. **grupo concurrente de pulsaciones**.

La representación final puede ajustarse durante implementación, pero debe preservar una estructura equivalente a:

```json
{
  "nombre": "presencia-y-rechazos",
  "precondicion": "backend en PREPARANDO con configuracion/padron de referencia",
  "pasos": [
    {
      "entrada": "1-9",
      "esperado": {
        "status_http": 200,
        "aceptada": true,
        "motivo": "PRESENCIA_ACTUALIZADA"
      }
    },
    {"pausa_ms": 100},
    {
      "concurrentes": [
        {"entrada": "2-9"},
        {"entrada": "3-4", "esperado": {"status_http": 200, "motivo": "TECLA_NO_HABILITADA"}}
      ]
    }
  ]
}
```

`precondicion` es informativa en WP-007: el simulador no debe inventar un segundo mecanismo para preparar/configurar el backend ni asumir control global de su ciclo de vida.

### 10. Expectativas opcionales

Una pulsación de escenario puede declarar expectativas. Deben ser **opcionales**: omitirlas significa enviar y observar sin convertir el paso en una aserción.

El conjunto mínimo de expectativas soportadas es:

- `status_http`;
- `aceptada`;
- `motivo`.

Para `aceptada`/`motivo`, si el body no es JSON válido o no tiene la estructura necesaria, la expectativa falla con diagnóstico claro; la salida literal recibida se conserva.

No implementar en WP-007 un lenguaje general de JSONPath, expresiones arbitrarias ni un framework de assertions extensible.

Un escenario termina con código distinto de cero si al menos una expectativa no se cumple, existe un error de sintaxis/formato del escenario o una pulsación requerida no puede ejecutarse.

### 11. Concurrencia real desde el simulador

Un grupo `concurrentes` debe iniciar sus requests de modo concurrente real, utilizando las primitivas asíncronas ya disponibles en el entorno Python del proyecto.

El simulador no debe imponer artificialmente el orden de procesamiento del backend ni interpretar cuál request "debería ganar". El único orden oficial continúa siendo el que el backend serializa conforme a DT-004/CA-058.

El objetivo de la concurrencia del simulador es poder reproducir presión simultánea y observar/verificar las respuestas sin compartir estado mutable inseguro dentro de la herramienta.

### 12. Escenarios iniciales versionados

WP-007 debe incluir escenarios de referencia compatibles con las capacidades ya integradas, sin adelantarse a WP-008 o posteriores.

Como mínimo:

- presencia mediante tecla `9`;
- test mediante tecla `8`;
- dispositivo lógico no asignado;
- tecla conocida pero no habilitada en `PREPARANDO`;
- al menos una tecla/entrada sin semántica funcional actual para comprobar rechazo controlado;
- grupo concurrente de pulsaciones.

Los escenarios que requieren `PREPARANDO` deben declarar esa precondición. No deben abrir sesión, crear votaciones ni simular resultados todavía inexistentes.

DT-024 menciona escenarios futuros como votación simple, empate, pérdida de quórum y concurrencia. WP-007 implementa el **motor** que permitirá agregarlos gradualmente; solo versiona ahora los que el backend integrado puede ejecutar de forma legítima.

### 13. No duplicar reglas del backend

El simulador puede interpretar `status_http`, `aceptada` y `motivo` únicamente para mostrar una ayuda humana o evaluar una expectativa declarada.

No debe contener lógica como:

- "tecla 9 debe cambiar presencia";
- "tecla 8 debe durar N segundos";
- "tecla 1 significa positivo";
- "con X presentes hay quórum";
- "esta votación debería cerrar".

Esas reglas pertenecen al backend y a los escenarios/tests que declaran expectativas, no al motor del simulador.

Esto permite que el simulador continúe útil cuando futuros WPs amplíen la semántica de la misma ruta.

### 14. Documentación de uso para personas

`tools/device-simulator/README.md` debe actualizarse y convertirse en una guía práctica breve que incluya:

- requisito de tener un backend accesible;
- comando para modo interactivo;
- ejemplos `1-9`, `12-8`, `3-+`, `5--`, `4-enter`;
- comando para pulsación única;
- cambio de URL base;
- ejecución de un escenario;
- formato mínimo del JSON;
- cómo interpretar salida literal, resumen y códigos de salida;
- cómo salir/obtener ayuda en modo interactivo;
- aclaración de que el simulador trabaja con `devXX` lógicos y no con fingerprint/HID físico.

La documentación debe ser suficiente para que una persona sin conocimiento de la estructura interna de FastAPI pueda utilizar la herramienta para pruebas manuales.

## Criterios de aceptación

1. Existe una CLI Python funcional bajo `tools/device-simulator/` y puede ejecutarse con `uv` sin hardware físico.
2. La CLI envía pulsaciones exclusivamente por `POST /api/v1/entradas/tecla` usando `{dispositivo, tecla}`.
3. Sin argumentos de pulsación/escenario abre un modo interactivo persistente y sencillo.
4. La sintaxis manual `5-9` produce exactamente `dispositivo=dev05`, `tecla=9`.
5. `12-8` produce `dispositivo=dev12`, `tecla=8`.
6. `5--` se parsea correctamente como dispositivo `dev05` y tecla `-`.
7. Un número que no corresponde al padrón, por ejemplo `99-9`, puede enviarse normalmente; el simulador no lo bloquea por reglas de negocio.
8. Una tecla distinta de las actualmente funcionales, por ejemplo `4`, `+` o un token textual no vacío, puede enviarse; el simulador no la rechaza localmente por semántica.
9. Cada request enviado muestra status HTTP y body literal recibido, incluso para `4xx/5xx`.
10. La salida literal no se reemplaza por pretty-print ni por un DTO reconstruido.
11. Un error de sintaxis manual no envía request y en modo interactivo permite continuar.
12. Un error de conexión/timeout se diagnostica sin traceback operativo innecesario y en modo interactivo permite continuar.
13. Existe modo de pulsación única con código de salida determinista/documentado.
14. Existe ejecución de escenarios JSON con pulsaciones secuenciales, pausas y grupos concurrentes.
15. Las expectativas `status_http`, `aceptada` y `motivo` son opcionales y, cuando existen, determinan éxito/fallo del escenario.
16. Un incumplimiento de expectativa produce código no cero y conserva visible la respuesta literal que originó el fallo.
17. Los grupos concurrentes generan requests concurrentes reales sin duplicar la serialización del backend en el cliente.
18. Existen escenarios versionados mínimos para presencia, test, dispositivo no asignado, tecla no habilitada/no contemplada y concurrencia, con precondiciones explícitas cuando corresponda.
19. El simulador no contiene lógica de negocio propia para presencia, quórum, voto, palabra, sesión o auditoría.
20. El simulador no importa servicios internos de FastAPI para producir pulsaciones.
21. `tools/device-simulator/README.md` permite a un usuario ejecutar pruebas manuales sin conocer internamente el backend.
22. No se incorpora GUI/TUI compleja ni hardware/HID real.
23. No se agrega una nueva dependencia externa sin necesidad aprobada.
24. El código propio nuevo respeta nomenclatura en español según DEC-001.
25. Clases, funciones y flujos no triviales están documentados/comentados en español con finalidad pedagógica.
26. Las consultas técnicas externas y los fallbacks de herramientas respetan DEC-003 cuando corresponda.
27. El inicio, rama/worktree y selección/revisión de agentes respetan DEC-007.
28. No se modifican contratos funcionales del backend para hacer pasar el simulador.

## Pruebas obligatorias

Deben agregarse pruebas automatizadas del simulador que cubran como mínimo:

- parsing `5-9 -> dev05/9`;
- parsing `12-8 -> dev12/8`;
- parsing `5-- -> dev05/-`;
- rechazo local de entradas sin separador, dispositivo no numérico o tecla vacía;
- aceptación local de dispositivo lógico inexistente y de teclas no conocidas por el motor;
- composición de URL base + endpoint;
- request HTTP exacto enviado al backend mockeado;
- preservación del body literal para respuesta JSON válida, JSON desconocido y body no JSON;
- salida visible para respuesta `4xx/5xx`;
- continuidad del modo interactivo después de error de sintaxis y error de red;
- códigos de salida del modo de pulsación única;
- parseo/validación del formato de escenario;
- expectativas opcionales satisfechas e incumplidas;
- grupo concurrente que demuestra solapamiento/concurrencia de requests sin depender del orden de resolución del backend;
- escenarios de referencia cargables y válidos;
- regresión de la suite existente.

Checks obligatorios aplicables:

```text
uv run ruff check .
uv run ruff format --check .
uv run pyright
uv run pytest
git diff --check
```

Las pruebas normales no deben requerir hardware, red externa ni un proceso FastAPI vivo. Las llamadas HTTP deben poder mockearse/injectarse en la suite del simulador.

Puede agregarse una prueba de integración contra la aplicación FastAPI in-process si aporta valor y respeta la suite existente, pero no debe reemplazar las pruebas unitarias deterministas.

## Invariantes y restricciones

- FastAPI sigue siendo la única autoridad de reglas y estado.
- El simulador representa un cliente lógico externo, no una capa interna del backend.
- `dispositivo` enviado es lógico (`devXX` o equivalente construido), nunca fingerprint físico.
- La misma ruta `/api/v1/entradas/tecla` debe poder extenderse por WPs futuros sin reescribir el motor del simulador.
- Un rechazo funcional `200` no se transforma localmente en una regla de negocio diferente.
- Las respuestas literales del backend se conservan visibles para diagnóstico.
- No se filtran localmente teclas por su semántica funcional.
- No se crea una segunda fuente de verdad para quórum, presencia, voto o estado.
- No se anticipan entidades ni contratos de WPs posteriores.
- Las pruebas del simulador no dependen de hardware físico.
- Aplican las restricciones de DT-038: cualquier necesidad de cambiar arquitectura, contrato HTTP, dependencia o responsabilidad transversal debe escalarse antes de continuar la parte afectada.
- Aplican DEC-001, DEC-003 y DEC-007 como decisiones transversales obligatorias.

El simulador implementa un contrato nuevo de tooling y su interacción manual queda definida por este WP. No debe copiar la herramienta histórica por defecto.

Si aparece una ambigüedad de **comportamiento funcional del sistema** que afecte las expectativas de un escenario:

1. verificar primero las fuentes canónicas de WP-007 y WP propietario de esa regla;
2. si sigue sin estar definida, aplicar DEC-001 y consultar únicamente el código necesario de `martinebene/Botonera/main`;
3. registrar en la PR qué se verificó;
4. si producción tampoco lo define, escalar antes de inventar.

No utilizar producción como fallback para decidir arquitectura del simulador, formato técnico de escenarios o dependencias.
