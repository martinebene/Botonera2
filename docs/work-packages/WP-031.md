# WP-031 - Lanzamiento de agentes sin prompt automático

## Estado documental

`BORRADOR`

## Objetivo

Separar de forma explícita las responsabilidades del launcher y del orquestador: los scripts de inicio deben limitarse a validar el estado operativo, sincronizar el repositorio, crear o reutilizar correctamente el worktree/rama y abrir el agente asignado; el prompt exhaustivo debe ser redactado por ChatGPT Web/orquestador, mostrado al operador en la interfaz y trasladado manualmente por el operador al agente.

## Resultado esperado

El flujo Orca debe poder iniciar un WP autorizado y abrir el agente correspondiente sin enviarle automáticamente ningún prompt de trabajo.

El operador debe recibir el prompt exhaustivo directamente de ChatGPT Web, poder leerlo/revisarlo y copiarlo/pegarlo manualmente en la sesión del agente abierta por Orca.

El lanzador genérico debe conservar el mismo principio de separación de responsabilidades: preparar el entorno y abrir la CLI del agente sin intentar convertirse en generador, validador, transportador u orquestador de prompts.

WP-031 elimina específicamente la brecha actual por la cual `scripts/iniciar_wp_orca.py` construye y envía un prompt inicial breve que no cumple la política de `PROMPTS_AGENTES.md`.

## Decisión operativa cerrada con el operador

El operador decidió que el launcher **no debe trasladar automáticamente el prompt al agente**.

La separación de responsabilidades queda así:

1. ChatGPT Web/orquestador reconstruye el estado real, planifica el WP y redacta el prompt exhaustivo específico para la tarea.
2. El launcher realiza únicamente trabajo mecánico y verificable de entorno/Git/Orca.
3. El launcher abre el agente asignado sin prompt inicial de trabajo.
4. ChatGPT Web muestra el prompt completo al operador en la conversación.
5. El operador puede leerlo, revisarlo y aprender de él antes de copiarlo/pegarlo manualmente en el agente.
6. El agente ejecuta ese prompt dentro del worktree ya preparado.

Esta decisión es deliberada: la revisión humana visible del prompt forma parte del flujo y no se considera una fricción que deba automatizarse.

La documentación oficial vigente de Orca distingue `--agent`, que abre el agente seleccionado, de `--prompt`, que opcionalmente le envía trabajo inicial. WP-031 aprovechará esa separación y no utilizará `--prompt` en el lanzamiento normal.

## Problema a resolver

El launcher Orca integrado actualmente contiene `construir_prompt_inicial()` y agrega `--prompt <texto>` a `orca worktree create`.

Ese prompt es deliberadamente breve y no puede sustituir el prompt exhaustivo que debe producir el orquestador. Mantenerlo crea dos problemas:

- el agente puede comenzar a trabajar antes de recibir las instrucciones completas;
- el operador puede asumir que el launcher ya trasladó suficiente contexto cuando en realidad todavía falta el prompt específico preparado por ChatGPT Web.

El lanzador genérico ya abre la CLI del agente sin inyectar un prompt de trabajo, por lo que su comportamiento conceptual está más cerca de la separación aprobada.

## Alcance

- Modificar `scripts/iniciar_wp_orca.py` para que `orca worktree create` abra el agente asignado sin argumento `--prompt`.
- Retirar del launcher Orca la generación de `construir_prompt_inicial()` y cualquier código que exista exclusivamente para transportar ese prompt automático.
- Mantener `--agent <agente>` y las demás opciones necesarias para que Orca cree el worktree, ejecute setup, active el workspace y abra el agente.
- Preservar todas las validaciones existentes de checkout coordinador, sincronización con `origin/main`, autorización del WP, dependencias, agente asignado, runtime Orca, repositorio registrado y ausencia de conflictos.
- Mantener la evidencia/verificación de que Orca creó correctamente el worktree y abrió una terminal/agente.
- Ajustar los tests del launcher Orca para verificar expresamente que el comando generado no contiene `--prompt` ni texto de tarea generado por el script.
- Mantener el lanzador genérico sin inyección automática de prompts.
- Actualizar la documentación operativa para establecer que, después de abrir el agente, el operador pega manualmente el prompt entregado por ChatGPT Web.
- Mantener `PROMPTS_AGENTES.md` como contrato de calidad del prompt que redacta el orquestador, no como especificación de generación automática del launcher.

## Fuera de alcance

- Generar prompts desde Python.
- Validar semántica o estructura del prompt mediante scripts.
- Guardar prompts en archivos temporales o versionados para que el launcher los lea.
- Pasar prompts por stdin, argumentos CLI, variables de entorno, clipboard automatizado, emulación de teclado o `orca terminal send`.
- Crear plantillas automáticas de implementación, corrección, revisión o re-revisión dentro de los scripts.
- Automatizar el lanzamiento del revisor desde el launcher inicial.
- Hacer que el launcher inspeccione PR, SHA candidato o hallazgos de revisión.
- Cambiar reglas de negocio, backend, frontends, simulador o `device-bridge`.
- Hacer que un lanzador apruebe WPs, cambie `PLAN.md` o tome decisiones reservadas al operador/orquestador.
- Hacer merge automático de PRs o saltar la revisión independiente.
- Seleccionar de forma rígida un único implementador, revisor o modelo para todos los WPs.
- Sustituir WP/DEC/documentación canónica por prompts.
- Introducir un orquestador autónomo que elimine la autorización humana en transiciones reservadas.

## Criterios de aceptación

1. `scripts/iniciar_wp_orca.py` sigue validando que el checkout coordinador sea correcto, esté limpio y sincronizado con `origin/main`.
2. El launcher sigue validando WP aprobado, estado `EN_CURSO`, agente asignado y dependencias integradas.
3. El launcher sigue validando runtime Orca, repositorio registrado y ausencia de conflictos previos.
4. El comando `orca worktree create` sigue incluyendo el agente asignado mediante `--agent`.
5. El comando de creación normal **no incluye `--prompt`**.
6. El launcher no construye, almacena, valida ni transporta texto de trabajo para el agente.
7. Orca sigue abriendo correctamente la terminal/agente y el launcher conserva evidencia suficiente para comprobarlo.
8. El operador recibe el prompt exhaustivo desde ChatGPT Web como paso separado y manual del procedimiento documentado.
9. `PROMPTS_AGENTES.md` sigue exigiendo prompts exhaustivos de implementación, corrección, revisión y re-revisión, pero asigna su redacción/entrega al orquestador y al operador, no al launcher.
10. El lanzador genérico conserva su comportamiento actual de abrir la CLI del agente sin inyectar un prompt automático.
11. Los tests fallan si `--prompt` vuelve a incorporarse accidentalmente al comando Orca normal.
12. Se preservan todas las pruebas de regresión y puertas de seguridad existentes de WP-030.
13. No se automatizan decisiones humanas reservadas, integración, revisión ni merge.
14. El código propio modificado respeta nomenclatura/documentación pedagógica de DEC-001.
15. Las consultas técnicas externas respetan DEC-003 cuando corresponda.
16. El WP conserva el formato parseable exigido por `FORMATO_WP_LANZADORES.md`.

## Pruebas obligatorias

- Tests unitarios del constructor de comando Orca demostrando presencia de `--agent` y ausencia de `--prompt`.
- Regresión completa de `tests/test_iniciar_wp_orca.py`.
- Verificación de que las validaciones previas a crear el worktree siguen fallando cerrado ante estados inválidos.
- Verificación de que la respuesta de Orca continúa exigiendo evidencia suficiente del worktree creado y del agente/terminal iniciado.
- Regresión del lanzador genérico si el cambio toca código compartido.
- Suite completa Python.
- Puertas globales de CI vigentes al momento de la implementación.
- `git diff --check`.

Los tests no deben requerir un runtime Orca real; deben continuar usando simulación/inyección determinista como la suite vigente.

## Invariantes y restricciones

- El repositorio y la documentación canónica siguen siendo fuente de verdad.
- El prompt exhaustivo sigue siendo responsabilidad de ChatGPT Web/orquestador.
- El operador conserva una instancia humana explícita entre la redacción del prompt y su ejecución: lo recibe, puede leerlo/revisarlo y lo pega manualmente en el agente.
- El launcher no interpreta ni modifica el prompt porque no lo recibe.
- Ningún launcher puede autoautorizar un WP, alterar decisiones reservadas o integrar una PR.
- Deben preservarse DEC-004, DEC-005, DEC-007 y las validaciones existentes de autorización/entorno.
- La independencia de revisión continúa siendo secuencial y coordinada por el orquestador/operador fuera del launcher.
- Cualquier necesidad de volver a automatizar el transporte de prompts en el futuro requerirá una decisión explícita nueva; no debe reaparecer como refactor incidental.

## Flujo objetivo después de WP-031

```text
ChatGPT Web / orquestador
  -> planifica y autoriza documentalmente
  -> entrega comando de launcher al operador

launcher
  -> valida main/Git/WP/dependencias/agente/Orca
  -> crea worktree y rama
  -> abre agente SIN prompt de trabajo
  -> devuelve evidencia de worktree/rama/terminal

ChatGPT Web / orquestador
  -> muestra prompt exhaustivo al operador

operador
  -> lee/revisa el prompt
  -> copia y pega el prompt en el agente abierto

agente
  -> implementa siguiendo ese prompt
```

## Decisiones todavía abiertas antes de aprobar

Solo quedan decisiones de detalle menores que no deben cambiar la separación de responsabilidades aprobada:

- si el launcher debe imprimir al finalizar una línea informativa como `Agente abierto: pegá ahora el prompt entregado por el orquestador`, sin incluir el contenido del prompt;
- si conviene retirar completamente `construir_prompt_inicial()` o conservar temporalmente una compatibilidad interna no utilizada. La preferencia es retirarlo para evitar código muerto y que vuelva a usarse accidentalmente.

Estas decisiones pueden cerrarse en la planificación final antes de cambiar el estado a `APROBADO`.

## Herramientas MCP y documentación técnica externa

Si la implementación depende de comportamiento/versiones de Orca u otra CLI externa, aplicar DEC-003 y consultar documentación técnica vigente/fuentes primarias.

Para esta decisión ya se verificó en la documentación oficial de Orca que `--agent` lanza el agente seleccionado y que `--prompt` es una opción separada para enviar trabajo inicial, por lo que el flujo sin `--prompt` es compatible conceptualmente con la CLI vigente.
