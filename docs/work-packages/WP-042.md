# WP-042 - Stack interactivo de desarrollo con hot reload sobre main

## Estado documental

`APROBADO`

## Objetivo

Incorporar un modo de desarrollo interactivo adicional para el checkout coordinador de `main` que permita mantener abierto el túnel SSH y las pestañas del navegador mientras los cambios ya integrados en `main` se reflejan sin reconstruir manualmente las SPA ni reiniciar todo el stack.

El comando canónico nuevo será:

```bash
pnpm dev:stack:hot
```

Este modo complementa, no reemplaza, a `pnpm dev:stack`. El stack existente continúa siendo el harness integrado estático/reproducible que construye los artefactos antes de servirlos. El nuevo modo prioriza iteración visual rápida mediante servidores de desarrollo y hot module replacement (HMR).

La modalidad elegida por el HUMAN_GATE es **hot reload del checkout coordinador de `main`**. No debe mostrar cambios privados de worktrees de implementadores antes de su integración.

## Dependencias

- WP-033 `INTEGRADO`: harness integrado de desarrollo y mismo origen.
- WP-034 `INTEGRADO`: SPA web del simulador integrada al stack de desarrollo.

## Alcance

### 1. Nuevo comando interactivo

Agregar:

```bash
pnpm dev:stack:hot
```

Debe levantar en primer plano un stack interactivo compuesto por:

- FastAPI real en modo de desarrollo;
- Moderación mediante servidor de desarrollo Nuxt/Vite con HMR;
- Recinto mediante servidor de desarrollo Nuxt/Vite con HMR;
- Simulador mediante servidor de desarrollo Nuxt/Vite con HMR;
- una única superficie HTTP externa de loopback que preserve las subrutas canónicas y el mismo origen.

El comando no debe ejecutar `pnpm build` como precondición normal.

### 2. Rutas externas y mismo origen

Desde el navegador debe conservarse un único origen externo:

```text
/moderacion/
/recinto/
/simulador/
/api/v1/
/docs
/openapi.json
```

REST y SSE deben seguir usando FastAPI real bajo ese mismo origen. No agregar CORS para hacer funcionar este modo.

La implementación puede utilizar puertos internos auxiliares para FastAPI y los servidores Nuxt, siempre que:

- escuchen solo en loopback;
- no se expongan como interfaz recomendada al operador;
- no requieran cambios persistentes del VPS;
- se limpien al terminar el proceso padre.

### 3. HMR de los tres frontends

Una modificación de archivos fuente de cualquiera de las tres SPA dentro del checkout desde el que se ejecutó el comando debe provocar actualización HMR o recarga automática equivalente del navegador, sin:

- `pnpm build`;
- reinicio manual del stack;
- `Ctrl+F5`;
- cambio de URL.

El transporte HMR/WebSocket debe funcionar también cuando el operador accede a través del túnel SSH.

### 4. Recarga del backend

Los cambios de código Python del backend deben recargar automáticamente el proceso de desarrollo de FastAPI sin reiniciar manualmente todo el stack.

Como el estado institucional es deliberadamente volátil, una recarga de backend puede devolver el sistema a `SIN_PREPARAR`. La documentación debe advertirlo expresamente.

No implementar persistencia ni recuperación de estado para compensar el reload.

### 5. Semántica de main

Este modo está destinado al checkout coordinador de `main`.

Debe verificar al inicio que el checkout se encuentre en la rama `main`. Si no está en `main`, debe fallar con un mensaje accionable en lugar de fingir que se está mostrando el estado integrado.

No debe hacer automáticamente:

- `git fetch`;
- `git pull`;
- merge;
- rebase;
- checkout;
- reset;
- ninguna mutación Git.

Cuando el ORCHESTRATOR integre un WP en GitHub, el operador actualizará su checkout mediante:

```bash
git pull --ff-only origin main
```

Los cambios de archivos producidos por ese fast-forward deben ser detectados por los watchers ya activos y reflejarse en el navegador sin reconstruir ni reiniciar el stack.

El modo hot no observa ni lee worktrees ajenos para mostrar cambios previos al merge.

### 6. Puerto externo y túnel

Conservar como valor por defecto el contrato de desarrollo vigente en loopback. Si el tooling actual admite configurar puerto, el nuevo modo debe ofrecer una forma equivalente y documentada de elegirlo sin hardcodear el VPS.

Debe ser posible mantener el flujo usado por el operador con un único túnel SSH y las URLs habituales. Documentar ambos casos:

- puerto canónico del harness;
- ejemplo con puerto externo `18080` cuando el operador ya tiene ese túnel local configurado.

No modificar SSH, Docker, Tailscale, Caddy, Nginx, firewall, Supervisor ni servicios persistentes.

### 7. Gestión de procesos

El comando debe:

- permanecer en foreground;
- propagar una terminación normal a todos los procesos hijos;
- limpiar listeners auxiliares al recibir `Ctrl+C`;
- no dejar procesos Nuxt/Vite/Uvicorn/proxy huérfanos;
- terminar con error accionable si un componente esencial no puede iniciar;
- evitar esconder silenciosamente la caída de uno de los procesos hijos.

No usar `sudo`.

### 8. Stack estático existente

`pnpm dev:stack` debe conservar su comportamiento actual.

No convertirlo en HMR ni eliminar su build previo. Sigue siendo útil para verificar el resultado estático similar al artefacto que se servirá en producción.

### 9. Dependencias

Preferir las capacidades ya presentes en Node/Nuxt/Vite/Python y las dependencias fijadas en el repositorio.

No agregar una dependencia directa nueva solamente para resolver proxy/HMR sin escalar primero al ORCHESTRATOR conforme a DT-038.

No depender de ejecutables globales no versionados.

### 10. Documentación de uso

Actualizar la documentación de desarrollo para distinguir claramente:

```text
pnpm dev:stack      -> build estático + FastAPI; sin hot reload
pnpm dev:stack:hot  -> servidores de desarrollo + HMR; iteración visual sobre main
```

Debe incluir el flujo operativo:

1. iniciar `pnpm dev:stack:hot` una vez;
2. dejar abierto el túnel;
3. dejar abiertas Moderación/Recinto/Simulador;
4. después de integrar cambios remotos, ejecutar `git pull --ff-only origin main`;
5. observar la actualización automática del frontend;
6. si cambió backend Python, asumir que el reload puede reiniciar el estado en memoria;
7. finalizar con `Ctrl+C`.

## Fuera de alcance

- mostrar en vivo un WP antes de integrarlo en `main`;
- ejecutar el stack desde el worktree privado de un implementador como flujo canónico;
- sincronizar Git automáticamente;
- hacer polling de GitHub/origin;
- modificar el protocolo de orquestación;
- reemplazar `pnpm dev:stack`;
- modificar arquitectura o despliegue productivo;
- agregar CORS;
- persistir estado del backend;
- Docker/Compose;
- cambios de Tailscale, SSH, Nginx, Caddy, firewall o Supervisor;
- cambios de reglas institucionales, REST, SSE u OpenAPI;
- nuevas dependencias directas sin aprobación DT-038.

## Criterios de aceptación

1. Existe `pnpm dev:stack:hot`.
2. El comando no ejecuta un build estático como precondición normal.
3. Verifica que el checkout sea `main`.
4. No realiza operaciones Git automáticas.
5. Expone Moderación, Recinto y Simulador bajo sus subrutas canónicas desde un único origen.
6. `/api/v1/health`, `/docs` y `/openapi.json` siguen resolviendo contra FastAPI real.
7. REST usa FastAPI real y no mocks.
8. SSE usa FastAPI real y conserva la actualización en tiempo real.
9. HMR de Moderación funciona sin reinicio manual.
10. HMR de Recinto funciona sin reinicio manual.
11. HMR del Simulador funciona sin reinicio manual.
12. HMR/WebSocket funciona atravesando el mismo puerto externo que usa el túnel SSH.
13. Un `git pull --ff-only origin main` con el stack ya activo no requiere reiniciar el comando ni ejecutar `pnpm build` para que los cambios frontend sean observables.
14. Cambios Python del backend producen autoreload de desarrollo.
15. La documentación advierte que ese reload puede reiniciar el estado volátil.
16. Todos los listeners auxiliares quedan ligados exclusivamente a loopback.
17. `Ctrl+C` libera todos los puertos del stack.
18. La caída de un proceso esencial termina o degrada el stack de forma explícita; no queda ocultada.
19. `pnpm dev:stack` mantiene su comportamiento estático actual.
20. `pnpm dev:moderacion`, `pnpm dev:recinto` y `pnpm dev:simulador` continúan funcionando.
21. No se agrega CORS.
22. No se modifica backend funcional, contratos ni reglas institucionales.
23. No se agregan dependencias directas nuevas sin escalamiento.
24. El túnel SSH existente puede mantenerse como único acceso desde Windows.
25. La documentación explica claramente la diferencia entre modo estático y modo hot.
26. No se dejan procesos huérfanos después de finalizar.
27. Los gates generales del repositorio continúan verdes.

## Pruebas obligatorias

### Automatizadas

Agregar pruebas que cubran, como mínimo:

- validación de rama `main`;
- binding loopback de la superficie externa y procesos auxiliares;
- routing del mismo origen hacia las tres SPA y FastAPI;
- conservación de REST/SSE;
- gestión del ciclo de vida de procesos hijos;
- liberación de puertos al terminar;
- ausencia de regresión del stack estático existente;
- configuración necesaria para que HMR use el origen/puerto externo y no exponga accidentalmente puertos internos.

Cuando sea razonable, agregar una prueba E2E del nuevo stack que abra las tres rutas y verifique que el canal de desarrollo/HMR queda operativo.

### Smoke obligatorio en agent-dev

Sobre el candidato exacto:

1. iniciar `pnpm dev:stack:hot`;
2. comprobar `/moderacion/`, `/recinto/`, `/simulador/`, `/api/v1/health` y `/docs`;
3. verificar REST y SSE reales;
4. realizar una modificación visual temporal y reversible en Moderación y comprobar que el navegador cambia sin build/restart;
5. revertir exactamente esa modificación temporal;
6. repetir una comprobación equivalente en Simulador;
7. comprobar que el proceso principal siguió vivo;
8. modificar temporalmente de forma reversible un archivo Python observado por el backend o utilizar una técnica no destructiva equivalente para verificar autoreload;
9. revertir la modificación temporal;
10. confirmar que el backend vuelve a estar disponible y documentar el reinicio esperado del estado volátil;
11. finalizar con `Ctrl+C`;
12. confirmar que no quedan listeners/procesos hijos del stack.

El implementador debe dejar limpio el worktree antes de commit y no versionar los cambios temporales del smoke.

## Invariantes y restricciones

- FastAPI sigue siendo única autoridad institucional.
- HMR es tooling de desarrollo, no parte del runtime productivo.
- `main` es la única fuente que observa el modo canónico hot.
- No se copian cambios desde worktrees de implementadores.
- No se muta Git automáticamente.
- No se agrega persistencia de estado.
- No se introducen dependencias directas sin aprobación.
- No se relajan tests ni gates existentes.
- Aplican DEC-001, DEC-003, DEC-007 y DEC-017.
