# WP-108 - Convergencia fiable del postcheck de actualización productiva

## Estado documental

`APROBADO`

## Objetivo

Eliminar el falso `ESTADO_INCONSISTENTE` que puede aparecer inmediatamente después de una
actualización SIS-Leg -> SIS-Leg correctamente activada cuando el Device Bridge ya figura
`active` pero su listener de control en `:8765` todavía no está disponible, sin relajar la
clasificación formal ni ocultar inconsistencias reales.

El cierre de la actualización en caliente debe esperar de forma acotada y basada en evidencia a que
el host converja nuevamente a `ESTABLE_SISLEG`. Si esa convergencia no ocurre dentro del presupuesto,
la falla debe formar parte de la misma transacción operacional y disparar el rollback seguro a la
release/target previos.

## Resultado esperado

Una actualización en caliente sólo termina como éxito cuando el host convergió realmente a
`ESTABLE_SISLEG`. Una demora transitoria de readiness del bridge no genera un falso fallo; una
inconsistencia persistente continúa fallando cerrado y revierte la transacción cuando corresponda.

## Alcance

- Reproducir determinísticamente el defecto observado en producción:
  - SIS-Leg parte de `ESTABLE_SISLEG`;
  - la nueva release se activa y pasa health;
  - el bridge puede figurar `active` antes de que el listener `:8765` esté listo;
  - la clasificación inmediata puede devolver transitoriamente `ESTADO_INCONSISTENTE`.
- Incorporar una espera acotada por **condición observable**, no un sleep ciego, antes de dar por
  terminada la actualización en caliente.
- Mantener `InspectorEstadoHost.clasificar()` estricto: `ESTABLE_SISLEG` sigue requiriendo el
  puerto del bridge realmente disponible.
- Hacer que la comprobación de convergencia final sea parte de la transacción de actualización:
  si no converge, restaurar release y `target-release` previos mediante los mecanismos canónicos
  existentes y registrar el desenlace real del rollback.
- Conservar evidencia accionable del último estado observado en una falla.
- Mantener el flujo versionado de actualización y su historial coherentes con el desenlace real.
- Actualizar documentación operativa interna si la semántica de convergencia/rollback necesita ser
  explicitada.

## Fuera de alcance

- Cambiar la definición de `ESTABLE_SISLEG`.
- Eliminar o ignorar la sonda del puerto `:8765`.
- Aumentar timeouts mediante sleeps fijos sin una condición observable.
- Cambiar el protocolo del Device Bridge o su puerto.
- Cambiar systemd, Nginx, wrappers, launchers `.desktop`, sudoers o PolicyKit.
- Cambiar el canal público de releases.
- Cambiar reglas de negocio del recinto.
- Tocar producción durante este WP.
- Reintentar o reparar retrospectivamente el update productivo de WP-107, que ya quedó verificado
  estable.
- Refactors amplios ajenos al postcheck/convergencia.

## Criterios de aceptación

- Existe una regresión determinista que reproduce el patrón observado: bridge `active` con
  `:8765` todavía no disponible en el primer postcheck.
- Si el listener aparece dentro del presupuesto acotado, la actualización termina `EXITO`,
  `estado_final=ESTABLE_SISLEG`, con release y target nuevos y sin rollback.
- La espera consulta estado/evidencia real entre intentos; no es un `sleep` fijo utilizado como
  sustituto de una condición.
- Si el estado no converge dentro del presupuesto, la operación falla cerrado.
- Cuando la falta de convergencia ocurre después de activar la release nueva y/o actualizar target,
  se intenta restaurar la release realmente previa y el target previo como una única transacción
  operacional, y el historial refleja `ROLLBACK_EXITOSO` o `ROLLBACK_FALLIDO` según evidencia.
- Una inconsistencia real no queda convertida en éxito por tolerancia temporal.
- No se relaja `InspectorEstadoHost.clasificar()` ni se elimina la exigencia del puerto 8765.
- El caso Legacy -> sólo preparación/target conserva su semántica actual.
- Idempotencia y guard institucional continúan intactos.
- El código propio nuevo respeta nomenclatura en español y comentarios pedagógicos de DEC-001.
- El impacto sobre `manual/index.html` queda evaluado explícitamente.
- El documento conserva el formato parseable exigido por `FORMATO_WP_LANZADORES.md`.

## Pruebas obligatorias

Como mínimo:

1. regresión del falso negativo: la sonda de `:8765` falla inicialmente y luego converge;
2. convergencia inmediata sin espera adicional significativa;
3. listener `:8765` que nunca aparece: timeout/falla cerrada;
4. rollback completo cuando la no convergencia ocurre después de la activación;
5. clasificación/inconsistencia real que no debe ser aceptada como estable;
6. update desde `ESTABLE_LEGACY` sin cambio de comportamiento;
7. historial/resultados coherentes para éxito, falla y rollback;
8. suite completa aplicable:
   - `uv run ruff check .`;
   - `uv run ruff format --check .`;
   - `uv run pyright`;
   - `uv run pytest`;
   - `git diff --check`.

Si existe una suite más específica para `operaciones_host`, ejecutarla además de la suite completa.

## Impacto en el manual de usuario y soporte

`No requiere actualización del manual.`

El comportamiento visible esperado del botón/script «Actualizar SIS-Leg» no cambia: una actualización
sana debe terminar correctamente y una actualización realmente fallida debe revertirse e informar
falla. WP-108 corrige un falso negativo interno y completa la garantía de rollback ya documentada;
no agrega pasos, opciones ni configuración para la persona operadora. La documentación técnica de
soporte interno sí debe quedar consistente.
