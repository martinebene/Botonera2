# WP-035 - Ajustes de layout y cantidad dinámica del simulador visual

## Estado documental

`APROBADO`

## Objetivo

Ajustar exclusivamente la SPA `/simulador/` después de la primera prueba humana para reorganizar los seis controles de cada dispositivo y permitir elegir cuántos dispositivos lógicos se muestran.

## Dependencias

- WP-034 `INTEGRADO`: SPA visual, entrada directa a FastAPI, log y sincronización ya disponibles.

## Fuentes canónicas obligatorias

- `AGENTS.md`;
- este WP;
- `docs/work-packages/WP-034.md`;
- `docs/decisions/DEC-006-entrada-logica-presencia-test-y-quorum.md`;
- `apps/simulador/`;
- `packages/api-client/`.

## Alcance

### 1. Grilla interna exacta 2×3

Cada tarjeta mantiene únicamente su identificador lógico y las seis acciones existentes.

| | Columna 1 | Columna 2 | Columna 3 |
|---|---|---|---|
| Fila superior | Presencia, tecla `9` | Test, tecla `8` | Palabra, tecla `7` |
| Fila inferior | Afirmativo, tecla `1` | Abstención, tecla `2` | Negativo, tecla `3` |

La acción de presencia conserva su semántica neutra de alternancia y puede mantener la etiqueta compacta `Pres. / Aus.`. Este WP fija posición y función, no cambia reglas institucionales.

### 2. Selector de cantidad

Incorporar en la zona superior un control compacto `− / cantidad / +`.

Reglas:

- mínimo `1`;
- máximo `20`;
- valor inicial al cargar la SPA: `12`;
- sin campo de texto libre;
- `−` no baja de 1 y `+` no supera 20;
- al disminuir se ocultan solo los dispositivos de mayor número;
- al aumentar reaparecen en orden continuo;
- cantidad 8 => `dev01..dev08`;
- cantidad 20 => `dev01..dev20`;
- el valor es local de UI y no se persiste.

### 3. Dispositivos dev13..dev20

El frontend debe poder generar `dev13..dev20` con el mismo formato de los existentes.

No se agregan concejales, bancas, mappings físicos ni datos de padrón. Si un dispositivo no está asignado en el padrón activo, FastAPI puede responder `DISPOSITIVO_NO_ASIGNADO`; ese rechazo es diagnóstico válido y debe mostrarse normalmente en el log. El simulador no debe bloquear localmente esos identificadores.

### 4. Responsive

Se conserva el requisito de que los 12 dispositivos por defecto sean utilizables de forma compacta en Full HD. Para cantidades mayores puede existir scroll controlado si la resolución no permite mostrar todo sin degradar la usabilidad.

No introducir paginación, carrusel ni pestañas.

## Fuera de alcance

- cambios de backend;
- cambios de padrón o `system.toml`;
- cambios de `devices.json`;
- hardware físico;
- cambios de Moderación o Recinto;
- persistencia de la cantidad seleccionada;
- reglas frontend de aceptación/rechazo;
- rediseño general del panel de diagnóstico o del log.

## Criterios de aceptación

1. Cada tarjeta usa exactamente 2 filas × 3 columnas.
2. Fila superior: Presencia 9, Test 8, Palabra 7.
3. Fila inferior: Afirmativo 1, Abstención 2, Negativo 3.
4. El mapping HTTP 1/2/3/7/8/9 no cambia.
5. Existe selector `− / cantidad / +` visible arriba.
6. El valor inicial es 12.
7. El rango permitido es 1..20.
8. Reducir de 12 a 8 deja exactamente `dev01..dev08`.
9. Volver a subir restaura los identificadores sucesivos.
10. Cantidad 20 muestra `dev01..dev20`.
11. `dev13..dev20` llegan al backend real sin filtrado frontend.
12. No se modifica backend, bridge, padrón ni contratos.
13. Se mantienen concurrencia, cero retry y log real de WP-034.

## Pruebas obligatorias

- tests de orden de las seis acciones;
- valor inicial 12 y límites 1/20;
- decremento/incremento y continuidad de identificadores;
- render de `dev20`;
- pulsación desde un identificador >12 sin filtrado frontend;
- regresión de mapping exacto 1/2/3/7/8/9;
- Playwright con cantidad 12 y al menos un cambio de cantidad;
- gates generales del repositorio.
